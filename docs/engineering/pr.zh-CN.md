## 它做什么

`pr` 定义的是 pull request 正文的样子：一段展示变更的 **Summary（摘要）**、证明它可用的 **Evidence（证据）**，以及一个关于“落地风险有多大”的 **Merge Danger（合并风险）** 判断。它是一份格式参考，不是一套工作流。它不推分支、不开 PR、也不决定往里面放什么。它告诉[智能体](https://www.aihero.dev/ai-coding-dictionary/agent)，写 PR 正文时它该长什么样。

摘要是一幅图，不是一段话。默认的 PR 正文用散文描述 diff。这一份挑的是能把要点讲清的**最小视图**（伪代码、调用树、组件树、文件树、Mermaid 图，或一个塑形过的 diff），并让它周围的文字保持简短。评审者手边已经开着 diff，所以正文要做的是在他们读之前先给他们看它的形状。

## 何时该用它

输入 `/pr`，或者每当智能体在写 PR 正文时自动取用它。

| 你的处境 | 用哪个 |
| --- | --- |
| 一条分支已就绪，需要一份评审者能扫读的正文 | `pr` |
| 代码写完了，但还没有人评审过 | 先 [code-review](https://aihero.dev/skills-code-review)，再 `pr` |
| PR 已打开，评审意见正在回来 | 这套技能里还没有能干的；`pr` 只写正文 |

## 模板

三个部分，按这个顺序：

- **Summary（摘要）**：一幅或多幅小图，每幅紧挨着它支撑的那段短文。用一幅，有时几幅，很少全用。只保留评审者需要的调用、文件、属性和边界。
- **Evidence（证据）**：一个前后对比。当变更是视觉性的、且[环境](https://www.aihero.dev/ai-coding-dictionary/environment)拍得了截图时，截图是最强证据。否则，用那条以前失败、现在通过的测试（写成伪代码），或那段变了的控制台输出。
- **Merge Danger（合并风险）**：这个变更是**单向门（one-way door）**还是**双向门（two-way door）**，以及它的**波及半径（blast radius）**。双向门逆转起来便宜；单向门（破坏性迁移、公开 API 的删除、难以逆转的决定）不便宜。波及半径点明“如果这个变更是错的，什么可能坏掉”：布局位移、某个 API 的消费方、移动端响应式表现。

门的判断是首要理念。它把“这合并安全吗？”从一种直觉变成一条评审者可以反对的明确断言。它还告诉评审者把[人工评审](https://www.aihero.dev/ai-coding-dictionary/human-review)花在哪。波及半径小的双向门扫一眼，单向门慢慢读。

## 常见问题

**智能体自己做的门判断能信吗？**

不能盲信，而把它写明正是用意所在。写下变更的智能体同时也是给它打分的那个，所以它说“双向门、小波及半径”时要最起疑。diff 也常常藏住一个变更能否逆转这件事。正如一位用户所说：“回滚一个 commit 撤不回已发出的一批邮件”；一次带开关的灰度发布，也只在第一次写入以新格式落地之前是双向的。技能给智能体的是一个定义（破坏性动作和难以逆转的决定是单向的），不是一张清单，所以 Merge Danger 那一行要查得最仔细。两件事有帮助：确保智能体面前有[工单](https://www.aihero.dev/ai-coding-dictionary/ticket)或[规格](https://www.aihero.dev/ai-coding-dictionary/spec)，而不只是 diff；把你这个仓库永远视为单向的变更（schema 迁移、任何对外发布或删除的东西）写下来，放在智能体做判断之前会读到的地方。

**它替我把 PR 开出来吗？**

不。`pr` 只管正文。[implement](https://aihero.dev/skills-implement) 以提交到当前分支收尾。要一个开 PR 的技能或选项（一个 `/to-pr`，或让 `implement` 开 PR 而不是提交）的请求仍是未决议题。一位用户的绕法是给 `implement` 加一句本地覆盖，叫它开一个 PR。[implement-spec](https://aihero.dev/skills-implement-spec) 是例外：当你的 issue 跟踪器通过 PR 关闭工作、或你主动要求时，它会开一个 draft PR。因为 `pr` 可被模型调用，所以只要你叫智能体开 PR，它就用这个形状写正文。

**它不会又产出一墙的文字和图吗？**

技能的设计就是为了阻止这个，但它仍可能发生。用户对智能体 PR 正文的抱怨高度一致：“摘要很长，而我只想知道改了什么、怎么验证的、什么可能坏、合并安不安全。”技能告诉智能体跳过开场白、散文保持简短、挑最小视图，通常一幅图，很少全用。如果你拿到的还是一摞图，那是智能体把这话当耳边风了。如果正文巨大是因为 diff 巨大，问题在 PR 的尺寸，`pr` 不会替你拆它。

**我的仓库已经有 PR 模板了，听谁的？**

默认谁都不听。`pr` 有自己的模板，不会去找 `.github/pull_request_template.md` 之类的东西。好几位用户要求技能改用仓库的模板。如果你什么都不做，智能体就揣着两份针对同一文档、相互竞争的指示。在你仓库的智能体文档里把它定下来，比如：填仓库的模板，把 Summary、Evidence 和 Merge Danger 放在它下面。

**输出是 HTML 吗？为什么 Mermaid 图不渲染？**

输出是一份 markdown 的 PR 正文，不是 HTML 页面。GitHub 和 GitLab 会在 PR 描述里渲染 Mermaid 块，终端不会，所以图在智能体本地展示给你看的时候像一段原始文本。CLI harness 上的用户用 ASCII 的 Mermaid 渲染器、或让智能体给 PR 附一份 HTML 版本绕过去了。Mermaid 只是六种视图之一，调用树、文件树或塑形 diff 在哪儿读起来都一样。

**它能整理返回来的评审意见吗？**

不能。它写完正文就停。用户不止一次要求一种对其他开发者或评审机器人的意见做分诊的办法（哪些值得处理、哪些不是问题）。这个技能不做这件事。

**PR 变了之后它会把正文保持最新吗？**

不会。它在某个时间点写一次正文，一个在评审中不断变化的 PR 会让这份正文变陈旧。大改之后让智能体重写一遍。智能体又是在写 PR 正文，所以它用的还是同一个形状。

**我的变更没有 UI，Evidence 里放什么？**

除截图以外的一切。截图只有在变更是视觉性的时才是最强证据。对一次迁移、一个后台任务或一次重构，证据是那条以前失败、现在通过的测试，或那段变了的控制台输出。单独一句“测试是绿的”是一个断言，不是前后对比。

**它能把正文标记为 LLM 所写吗？**

它自己做不到。一位用户的做法是在仓库的智能体文档里放一条常设指示：智能体写的每个 issue、评论和 PR 都以一行披露收尾。这条规则属于仓库，在那里它能盖住智能体发布的所有东西，而不是放在一份只管一种文档的模板里。

## 有这些表现就说明它在生效

- 只看 Summary 的图，在打开 diff 之前，你就能说出这个 PR 改了什么。
- 正文没有开场白：它从 Summary 标题开始。
- Evidence 部分展示一个前和一个后，不是一句“测试通过”的断言。
- 每个 PR 都写明门和波及半径，而让你放慢速度的正是那些单向门。

## 它的位置

当构建以 pull request 的形式交付时，`pr` 位于评审和回顾之间：`to-spec → to-tickets → implement → code-review → pr → retro`。它是模型可调用的，所以在那条链之外，任何时候智能体写 PR 正文，它也会自己触发。

- [code-review](https://aihero.dev/skills-code-review) 跑在它前面，因为 PR 正文描述的应该是一个已被评审过的 diff。
- [implement](https://aihero.dev/skills-implement) 产出正文所描述的那些 commit。

拿不准处境要哪个技能时，[ask-matt](https://aihero.dev/skills-ask-matt) 带你在整套技能之间路由。
