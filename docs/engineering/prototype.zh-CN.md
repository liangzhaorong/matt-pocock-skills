## 它做什么

`prototype` 写的是**回答一个问题的一次性代码**：这个状态模型感觉对不对，或者这个界面该长什么样。问题在前，并决定你构建什么。一个回答错了问题的原型就是白费，无论它看起来多好。

一次性是对代码*怎么写*的约束，不是把它销毁的承诺。不写测试，不写超出“让它能跑”的错误处理，不做抽象，不做持久化，因为这些没有一个能帮你学到你想学的那一件事。有两样东西会留下来：答案进入真实代码，原型则落到一条从 main 分出来的分支上，作为答案的证据。

## 何时该用它

输入 `/prototype`，或者当任务合适时，[智能体](https://www.aihero.dev/ai-coding-dictionary/agent)自动取用它。

一旦你碰上一个靠谈话定不了的问题就找它：一台边界情况多得脑子装不下的状态机，一块要并排看到三个版本才能想象的界面。[拷问（grilling）](https://www.aihero.dev/ai-coding-dictionary/grilling)会话常常在这种问题上越拖越长。智能体换着说法问，你猜，范围越猜越大。停下拷问，把一次性版本做出来，看一眼，然后用一行话回答。反过来，如果是已经做好的东西行为异常、你想知道为什么，请用 [diagnosing-bugs](https://aihero.dev/skills-diagnosing-bugs)；原型探索的是该构建什么，不是已构建的东西为什么坏了。

你也会不经选择就走到这里。[wayfinder](https://aihero.dev/skills-wayfinder) 会在它的地图上立 `prototype` 类型的决策[工单](https://www.aihero.dev/ai-coding-dictionary/ticket)，你就用这个技能来做其中一张。

## 两条分支

问题决定走哪条分支，两条分支产出不同的东西：

- **“这个逻辑/状态模型感觉对不对？”**：一个**可分享的单个 HTML 文件**。一页自包含的页面，无需构建、无需服务器，双击就能打开。它带一块有标注的状态面板，每次点击后重新渲染；带自由把玩的按钮，可以按任意顺序戳这个模型；还带分标签页的**引导走查（guided walkthrough）**（每个标签页一个场景，场景下方列出按顺序要按的按钮）。所有东西都用领域语言标注，所以你可以把它递给设计师、PM 或领域专家，让他们自己上手试这个模型。页面背后的逻辑是一个小的纯模块（一个 reducer、一台机器、一组函数），里面没有 DOM 代码，验证过的版本可以直接搬进真实代码。
- **“这该长什么样？”**：同一路由上的几个**截然不同**的 UI 变体，从一个悬浮底栏和 `?variant=` URL 参数切换。变体必须在结构上分歧，而不是在颜色上；三个只微调了一下的卡片网格什么也回答不了。只要可能，它们就渲染在真实页面里，对着真实数据和真实密度，因为在空页面上评判的变体永远看起来挺好。

两者都把状态放在内存里，零配置启动，每一步之后都把完整状态摆给你看。一旦你发现自己开始加固某个原型（加测试、接真实数据库、为将来可能用得上的情况做泛化），你就已经不是在做原型了。

## 原型是一手来源

一个做完的原型留下两样东西，它们去不同的地方。

你把**答案**（结论加上它定下的那个问题）记录到某个永久的地方：commit message、ADR、实现 issue。main 以真实代码的形式把答案留下来。

**原型**是答案所出自的可运行证据，你不要删它。它也不属于 main，因为没人维护它，而且很快过时。所以你把它提交到一条从 main 分出来的、用完即弃的 `prototype/<name>` 分支，永不合并，并在实现 issue 上留一个指向那条分支的[上下文指针（context pointer）](https://www.aihero.dev/ai-coding-dictionary/context-pointer)。main 保持干净，下一个接手的人也能找到并重跑这个原型。

## 常见问题

**等等，原型不是应该删掉吗？**
现在不是了。以前是：做出来，留下答案，把代码扔进垃圾桶。对此最强的反对意见与速度无关，而是*下一个[会话](https://www.aihero.dev/ai-coding-dictionary/session)谁来接手这项工作、他们手上有什么可用？* 原型的散文摘要会丢掉让它有说服力的那个东西。所以这个技能现在把原型当作[一手来源](https://www.aihero.dev/ai-coding-dictionary/primary-source)。它落到一条从 main 分出来的 `prototype/<name>` 分支上，实现 issue 指向它。变的是代码住在哪，不是纪律；它依然永不合并进 main。

**它以前做的是终端应用，那去哪了？**
逻辑分支现在产出的是一个可分享的单个 HTML 文件。终端应用只有克隆了仓库、装了运行时的人才能开，这就把原型的意见恰恰需要的那批人排除在外：设计师、PM、知道状态模型到底该是什么意思的领域专家。一个双击打开、被邮件发过之后还能用的自包含文件，谁都能开。底下的纯逻辑模块没有变，也依然是你要搬进真实代码的那部分。

**有个智能体让我去 `/prototype`，可我当时该做的是实现。**
这是一个已知的命名问题。不了解流程的智能体把 `prototype` 这个泛泛又诱人的词读成“工单有了之后的显然下一步”。于是哪怕设计早在对话里定死了，智能体还是会点名推荐它。如果你已经知道要构建什么，下一步是逐张工单地 `/implement`。只有当某个具体的设计问题悬而未决、且谈话解决不了它时，才找原型。

**我该在构建任何生产功能之前先把整个应用原型化吗（比如演示给潜在客户看）？**
那是另一种东西，只是恰好和这个技能重名。这里的一个原型只装一个问题，而“整个应用长什么样”不是一个问题。全应用原型没有天然的停止点，于是会漂着漂着变成生产应用：清理那一轮永远不会来，按原型规则写的代码（没测试、没错误处理）最后出现在用户面前。如果你要的是销售演示，就故意把它当作演示来做，并明说其中没有一行是生产代码。如果你要定一个设计问题，就把它削到只剩那个问题。

**怎么在它自己的会话里运行？**
原型住在自己的目录里，会产生大量你不想要在提问线程里的[上下文](https://www.aihero.dev/ai-coding-dictionary/context)，所以把它放到别处跑，只把答案带回来。用 [handoff](https://aihero.dev/skills-handoff) 把工作挪进那个会话，再把答案带回来。

**这不是烧 [token](https://www.aihero.dev/ai-coding-dictionary/token) 最快的方式吗？**
可以是，如果你把本可以谈出来的问题拿去做原型，或者让一个原型摊满一整个功能。要紧的比较不是 token 对零，而是 token 对“构建了错误的状态模型、等它有了生产调用方才发现”。问题保持窄、运行保持短，花销就保持成比例。

## 有这些表现就说明它在生效

- 你能用一句话说出这个原型存在是为了回答什么问题，而且这句话写在演示的顶部，不是只在你脑子里。
- 不读代码的人也能开动逻辑演示。他们打开文件，按走查标签页里的按钮，用自己的话描述看到的东西。
- 有人说“等等，这不应该是可能的”或“咦，我原以为是 X”。那是*想法*里的 bug，而这正是原型存在的目的。
- UI 变体在布局和信息层级上分歧，而不只是颜色和文案，你收到的反馈是“B 的头部配 C 的侧栏”。
- 它一口气就回答完了。如果你一天之后还在搭它，说明问题太大了，拆开。
- 结束时，main 里有决定、没有原型，实现 issue 指向仍然装着它的那条分支。

## 它的位置

`prototype` 是一个**随取随用的独立件**：你用它定一个设计问题，然后回到你的工作。还有一个技能也会运行它。

最常运行它的是 [wayfinder](https://aihero.dev/skills-wayfinder)。wayfinder 的地图由**决策工单（decision ticket）**构成，`prototype` 是工单可以属于的四种类型之一：用在拦路问题是“这该长什么样”或“它该怎么表现”的时候，多少讨论都解决不了那种问题。当讨论含糊时，wayfinder 造一个具体的东西让人去反应，这个技能造那个东西。答案解决掉一张原型工单，地图把原型作为资产链接过去。

其他邻居在这条关系的上游和下游。[grill-me](https://aihero.dev/skills-grill-me) 和 [grill-with-docs](https://aihero.dev/skills-grill-with-docs) 回答可拷问的问题；不可拷问的转到这里来，一行式的答案再回到访谈里。下游，验证过的状态模型或 UI 方向成为 [to-spec](https://aihero.dev/skills-to-spec) 的定案输入，后者可以把原型产出的富决策片段直接内联，而不是用散文描述它。其他一切，[ask-matt](https://aihero.dev/skills-ask-matt) 带你路由整套技能。
