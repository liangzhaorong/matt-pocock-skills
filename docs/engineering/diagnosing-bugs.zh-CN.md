## 它做什么

`diagnosing-bugs` 对一个疑难 bug 或一次性能回退跑六阶段诊断：建复现、把它最小化、排假设、插桩、带回归测试修复、清理。

在一个**紧的**反馈回路存在之前，它不许智能体形成任何理论：一条有名有姓的命令，已经跑过一次，在*这个* bug 上变红、修好后变绿。拿到一份 bug 报告，编码智能体默认会读代码然后瞎猜。这个技能拦住那一手。如果不存在能变红的命令，就没有第二阶段。这一道闸就是技能存在的意义。回路一旦存在，它之后的一切（二分、假设检验、插桩）都是机械的。

## 何时该用它

输入 `/diagnosing-bugs`，或者当任务合适时智能体自动取用它。它是模型可调用的，在“诊断一下”或“调试这个”时触发，也在“某样东西坏了、抛异常、失败或变慢”的报告上触发。

难缠的才找它：一眼解不掉的 bug、间歇性的抖动、两个已知良好状态之间引入的回退。它故意又慢又彻底，所以对你想一条消息内得到回答的问题，它是错误的工具。

| 你的处境 | 去哪 |
| --- | --- |
| 一个能当成症状描述的具体缺陷 | 这个技能 |
| 一个慢掉的端点，或一次有已知前后对比的时序回退 | 这个技能。它有一条性能分支（先测基线，再二分） |
| “这个代码库的瓶颈在哪？”，没有具体症状 | 不是这个技能。它诊断一个已知的失败，不做审计 |
| 别人报来的一份原始 bug 报告，还没确认、没成文 | 先 [triage](https://aihero.dev/skills-triage) |
| 用一次性代码回答一个设计问题，而不是追一个缺陷 | [prototype](https://aihero.dev/skills-prototype) |
| 测试先行地构建一个计划中的行为 | [tdd](https://aihero.dev/skills-tdd) |
| 修好之后问“什么本可阻止这个 bug” | [retro](https://aihero.dev/skills-retro)，在同一场会话里跑 |
| 不存在能把 bug 锁住的好接缝 | [improve-codebase-architecture](https://aihero.dev/skills-improve-codebase-architecture)，由你自己发起 |

## 紧回路本身就是技能

第一阶段花最多力气，因为它是唯一难的阶段。技能列出了构建回路的方法，大致按偏好排序：

1. 在够得着 bug 的任意接缝上的一条失败测试。
2. 对着运行中的开发服务器的一条 curl 或 HTTP 脚本。
3. 一次带夹具输入的 CLI 调用，与已知良好的快照做 diff。
4. 一条对 DOM、控制台或网络做断言的无头浏览器脚本。
5. 一次重放的捕获：存下来的请求、载荷或事件日志，单独送进代码路径里跑。
6. 一个一次性试验架：系统的最小子集，一次函数调用。
7. 一个性质或模糊测试循环，对付“有时输出错误”。
8. 一个能交给 `git bisect run` 的二分试验架。
9. 一个差分回路：同一输入，旧版本对新版本。
10. 一个[人在回路（human-in-the-loop）](https://www.aihero.dev/ai-coding-dictionary/human-in-the-loop)的 bash 脚本，最后手段。技能为此随附 `scripts/hitl-loop.template.sh`：智能体跑脚本，你在终端跟着提示走，你的回答以可解析的输出形式返回。

有*一条*回路不是目标，**紧**才是：快（秒级）、确定（每次运行同一个结论）、锐利（断言你的确切症状，而不是“没崩”）、且智能体无需你就能跑。一条 30 秒、会抖的回路不比没有好多少。对一个只在有时出现的 bug，目标不是干净的复现，而是**更高的复现率**：循环触发、并行、加压、注入延迟，直到抖动率高到可以对着调试。

当智能体造不出回路时，技能叫它停下并明说，列出试过什么，并向你要[环境](https://www.aihero.dev/ai-coding-dictionary/environment)访问权、一份捕获的产物，或添加临时插桩的许可。它绝不许硬着头皮继续去形成假设。

## 阶段之间的闸门

这些阶段是闸门，不是清单。某个具体条件成立之前，智能体进不了下一个阶段。

| 闸门 | 什么必须为真 |
| --- | --- |
| 进第二阶段 | 一条有名有姓、已经跑过并连同输出贴出来的命令，它能在本 bug 上变红 |
| 进第三阶段 | 复现已复现*且*已最小化：剩下的每个元素都是复现 bug 所必需的 |
| 进第四阶段 | 存在 3 到 5 条排好序、可证伪的假设，每条都写明自己的预测，并在检验任何一条之前给你看过 |
| 进第五阶段 | 探针一一对应具体预测，一次只动一个变量，每条调试日志都带一个像 `[DEBUG-a4f2]` 这样的标签，清理时一次 grep 全找得到 |
| 完成 | 原始复现不再复现，插桩已清除，commit message 点名了最终正确的那个假设 |

第五阶段有一个例外。智能体在修复之前写回归测试，但前提是存在一条**正确的接缝**：测试能在调用现场驱动真实出现的 bug 模式。当唯一可用的接缝太浅时，技能叫智能体明说，而不是写一条给人虚假信心的测试。缺失的接缝本身就是一条发现，智能体把它记录下来，而不是藏起来。

## 常见问题

**它在我只想要个直接回答的快问题上也会触发。**
这是这个技能被报告得最多的问题。在 GPT-5.6-Sol 上尤其如此，用户报告它对一段平平常常的问题描述也会触发：“模型转而触发了那个相当正式的 diagnosing-bugs 技能。它接着构建一个复现场景（往往是搭一个价值有限的 mock 场景），然后才给我回应或建议。这导致回复明显变慢。”在 [issue #578](https://github.com/mattpocock/skills/issues/578) 上有四个人分别报告了同一问题。已接受的修法是先从轻量方式入手、只在问题需要时才进入完整诊断，但那个改动还没发布。这个技能是按 Claude Code 的调用行为调的，一个激活阈值更低的[模型](https://www.aihero.dev/ai-coding-dictionary/model)会过于频繁地触发它。在修复发布之前，绕法是说清楚你要什么（“直接回答这个，别诊断”），或在你的 [harness](https://www.aihero.dev/ai-coding-dictionary/harness) 里关掉它的模型调用。

**我能把它对准一个代码库，问性能问题在哪吗？**
不能。它诊断的是你已经叫得出名字的那一个失败。它的性能分支针对带症状的回退（先确立基线测量，再二分，先测量后修复），不针对主动扫荡。主动版技能曾被[提议后关闭](https://github.com/mattpocock/skills/issues/431)；现在没有技能做这件事。

**写修复之前它会停下来问我吗？**
不会。只有第三阶段有一个人工检查点：排好序的假设清单在检验任何一条之前给你看；你不在时，智能体按自己的排序继续。插桩和修复之间没有闸门，所以智能体可以在你还没认它的根因之前就开始写代码。[Issue #124](https://github.com/mattpocock/skills/issues/124) 要的就是那道闸，仍开着。想要它，调用技能时说清楚。

**这份 bug 报告我已经跑过 `/triage` 了，这是把同样的活再干一遍吗？**
部分是，而且两个技能都没说破。正如一位读者所说：“triage 的第 3 步本质上是 diagnosing-bugs 第一到二阶段的一个浅而有界的实例，但两份文件互不提及。”triage 做的是有界的“这到底是不是 bug、面在哪”一遍过；这个技能做完整版。先跑 triage 不算白费，它的验证常常已经给你第一阶段的大部分原材料。但预期这个技能会把那份工作完整重做一遍，而且不会有交叉引用告诉你这一点。

**它贴出来的复现输出会泄漏秘密吗？**
有可能。技能要求智能体贴出调用及其输出，并要求 HAR 文件、日志转储、core dump 这类产物。没有任何指示叫智能体给它们脱敏。[Issue #674](https://github.com/mattpocock/skills/issues/674) 提的正是这件事（凭据、token、cookie 和个人数据被复制进聊天、issue 或 PR），并提议一条脱敏护栏。它开着、未实现。眼下把脱敏当成你自己的活，尤其在输出要去任何公开地方之前。

**我的安全扫描器把这个技能标成高风险。**
Snyk 会标它，而这个标记是误报。它是整套技能里唯一随附可执行 shell 脚本（`hitl-loop.template.sh`）、还带着“运行它”和“curl 一个开发服务器”指示的技能。一个随附的 `.sh` 文件、运行它的指示、加上出站 HTTP，合起来就足以触发静态扫描器。脚本本身约 30 行 `read -r -p` 提示，用来暂停等人输入。扫描器评的是这个技能可能做什么，不是已被证实的利用。

**`/diagnose` 怎么了？**
v1.0.0 把它改名为 `/diagnosing-bugs`。旧名字不复存在。你手里任何串着 `/diagnose` 的东西（包装技能、存下来的提示词）都需要更新。

## 有这些表现就说明它在生效

- 它在给出任何一条理论之前，先给你看一条命令和它的红色输出。如果理论先到，技能就没有在运行。
- 它复现的失败就是你报告的那个，不是路上顺手找到的邻近某个。
- 它在开始猜之前先缩小复现，并能说出剩下的每一片为什么必需。
- 它在检验任何一条之前，先给你看一份 3 到 5 条的排序假设清单，每条都带一个你能证伪的预测。
- 它加的每条调试日志都带一个像 `[DEBUG-a4f2]` 的标签，它宣布完成时 grep 这个标签回来是空的。
- commit 或 PR 的 message 点名了哪个假设是对的。
- 当它无法用测试锁住 bug 时，它明说，而不是写一条浅的。

## 它的位置

`diagnosing-bugs` 是一个随取随用的独立件。东西坏了你启动它，修复和它的回归测试到位它就结束。它不保存状态，也不需要预先设置。[ask-matt](https://aihero.dev/skills-ask-matt) 把“有东西坏了”路由到这里。

两个邻居要紧。[retro](https://aihero.dev/skills-retro) 在它之后：修复一到位，就在同一场会话里跑它，趁会话比开场时知道得更多，问问什么本可阻止这个 bug。`diagnosing-bugs` 从不自己调用 `retro`，因为 `retro` 是用户调用的。对以原始报告形式从别人那里到达的 bug，[triage](https://aihero.dev/skills-triage) 在它之前，做同样前两阶段的一个更浅的版本。
