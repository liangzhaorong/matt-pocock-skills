**软件工厂（software factory）**是一个代理系统，把工单、PR 和日程变成合入的代码，部署在用户选择的远程基础设施上。本技能是设计它的语言。讨论或画白板时使用这些术语，而且只用这些；当用户伸手去用 *Avoid* 下的词时，点出规范术语。

## 任务与运行

**Task（任务）**：
工厂执行的一类工作，定义一次、运行多次：review、explore、implement、ratchet。一个任务可以作用于一张工单、一个 PR，或整个代码库。
_避免_：job、workflow、action 作为任务的名称。CI 厂商的 workflow 文件及其 job 是任务接线的地方，不是任务本身。

**Trigger（触发器）**：
启动一次运行的事件：工单跟踪器或 git 托管中的变化、编排器里的一座时钟，或另一次运行。

**Run（运行）**：
一个任务在一台运行器上的一次执行，从触发到结束，被视作黑盒。一次运行可以直接触发后续运行，可以经由编排器中的逻辑，也可以通过改动工单跟踪器或 git 托管。一次运行从不等待人类：它结束，而人类稍后对工单跟踪器或 git 托管的改动触发一次新的运行。
_避免_：session

**Runner（运行器）**：
一次运行在其上执行的一次性机器。机器上没有任何东西能在运行结束后幸存，即使机器本身长寿：一次运行对早先运行的唯一记忆，是工单跟踪器、git 托管和编排器。
_避免_：server、host、box、compute、sandbox

## 服务

**Ticket tracker（工单跟踪器）**：
工单所在之处，也是工厂的人类接口：人类通过提交工单安排工作，在工单评论里与代理对话，他们对工单的改动触发运行。
_避免_：issue tracker、ticket manager、project board

**Ticket source（工单来源）**：
工厂之外、在工单跟踪器里创建工单的任何东西：一个反馈按钮、一个监视器、一个错误跟踪器、一个收件箱。
_避免_：data source、trigger source、intake

**Git host（git 托管）**：
分支、PR 和评审所在之处。
_避免_：code host、forge、repo

**Orchestrator（编排器）**：
接收触发器、在运行器上启动运行、并记录哪些运行在排队、在途或已完成的组件。
_避免_：dispatcher、scheduler、control plane

**Observability platform（可观测性平台）**：
运行器向其发送日志、追踪和状态的地方，让人能看到每次运行内部发生了什么。可选：填运行器或编排器槽位的产品常常自己就显示得够多。在一次运行把某物写进工单跟踪器或 git 托管之前，永远不要替它做决定。
_避免_：observability、logs、monitoring、dashboard

## 设计工厂

设计有两半：**服务**，每个是一个由产品填充的槽位；以及**任务**，它们的运行让工作在这些服务之间流动。

从用户的问题出发，而不是从工厂出发：未分诊的工单堆积、等待自动评审的 PR、要迁移到的更严的自动化检查、没人读的 bug。当用户点名一个问题或不知道建什么时，读 [EXAMPLE-TASKS.md](EXAMPLE-TASKS.md) 找解决常见问题的任务。

### 缓慢启动

每个触发器都是油门。没有刹车的油门会造出一门垃圾加农炮（slop cannon）。有三个刹车：

- **自动化检查**：每次运行都必须通过的确定性闸门（类型、lint、测试）。
- **自动评审**：一个单独的运行，对照代码库的标准和工单（若有）冷读 diff。
- **人工评审**：人在 PR 合入前读它；它拦下的东西变成新的自动化检查和更锋利的自动评审。

一次只加一个自动触发器，起初先限流（十条 bug 报告取一条、一天只响一次的时钟），每个 PR 都带人工评审。随着刹车赢得信任再开油门，并把每一环运行的次数限制在人类介入前的少数几次。

### 填满每个槽位

每个服务是一个槽位。一个产品可以填几个槽位，一台服务器可以承载几个服务。三个设计并排：

| 服务 | 全在 GitHub | Linear 工单 | 自建跟踪器 |
| ---------------------- | ------------------------------- | ------------------------------ | ------------------------ |
| 工单跟踪器 | GitHub Issues | Linear | 自有应用 |
| 工单来源 | 反馈按钮 | 反馈按钮、监视器 | 反馈按钮、监视器 |
| Git 托管 | GitHub | GitHub | GitHub |
| 编排器 | GitHub Actions | 自有服务器 + 数据库 | 自有应用 |
| 运行器 | Actions runner | Actions、E2B、Daytona 或 VPS | 自有应用，或沙箱 |
| 可观测性平台 | 无：Actions 运行页足矣 | 某 LLM 追踪平台 | 自有应用 |

当用户在为某个槽位挑选产品时，先读该槽位的调研文件找方向，然后自己研究当前选项；每份调研按类型分组选项，并列出决定该槽位的问题：

- [TICKET-TRACKERS.md](TICKET-TRACKERS.md)
- [GIT-HOSTS.md](GIT-HOSTS.md)
- [RUNNERS.md](RUNNERS.md)
- [OBSERVABILITY-PLATFORMS.md](OBSERVABILITY-PLATFORMS.md)

买服务、建任务：任务承载用户的设计，服务是通用的。偏爱现成的工单跟踪器：它皮实、人们已经会用、外部用户也容易放进来。

### 质询每个任务

对每个任务，回答：

1. 什么触发它？
2. 它做什么，读写哪些服务？
3. 它接下来触发什么？
4. 人在哪里重新进入？
5. 什么阻止两次运行做同样的工作？

对每个工单来源，回答：什么阻止它把同一张工单提两遍？

当每个槽位都点上了产品（可观测性平台则可以是深思熟虑的"无"），且每个任务和工单来源对每个问题都有了答案，设计就完成了。
