对 `HEAD` 与用户提供的固定点之间的 diff 做两根轴的评审：

- **标准（Standards）**：代码是否符合本仓库写明的编码标准？
- **规格（Spec）**：代码是否忠实实现了原始的 issue/规格？

两根轴都作为**并行子智能体**运行，以免污染彼此的上下文，然后由本技能汇总它们的发现。每个子智能体都要以全新的上下文窗口启动。

issue 跟踪器应该已经提供给你。如果没有，就告诉用户运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 锁定固定点

用户所说的即为固定点（一个 commit SHA、分支名、tag、`main`、`HEAD~5` 等）。如果用户没有指定，就问用户要。

一次性定下 diff 命令：`git diff <fixed-point>...HEAD`（三个点，因此比较对象是 merge-base）。同时用 `git log <fixed-point>..HEAD --oneline` 记下 commit 列表。

在继续之前，先确认固定点可以解析（`git rev-parse <fixed-point>`）且 diff 非空。一个坏 ref 或空 diff 应该在这里就失败，而不是在两个并行子智能体内部失败。

### 2. 确定规格来源

按以下顺序寻找原始规格：

1. commit message 里的 issue 引用（`#123`、`Closes #45`、GitLab 的 `!67` 等），通过跟踪器文档中的工作流取回。
2. 用户当参数传进来的路径。
3. `docs/`、`specs/` 或 `.scratch/` 下与分支名或特性名匹配的规格文件。
4. 如果什么都没找到，就问用户规格在哪里。如果用户说没有规格，**规格**子智能体将跳过并报告“无可用规格”。

### 3. 确定标准来源

在仓库里搜索所有记载代码应当如何编写的文件。只要存在 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md`，它就必须在清单上。

在仓库已有记载的内容之外，标准轴永远携带下面的**坏味道基线**：一组固定的 Fowler 代码坏味道（《重构》第 3 章），即使仓库什么都没记载也适用。它受两条规则约束：

- **仓库压过基线。**仓库写明的标准永远获胜；凡仓库认可了某个基线会标记的东西，就抑制该坏味道。
- **永远是主观判断。**每个坏味道都是一条带标签的启发式（“可能是依恋情结”），从来不是硬性违规。和这里的任何标准一样，凡是工具已经强制执行的东西都跳过。

每个坏味道都按*它是什么* → *怎么修*来写；拿它对照 diff：

- **诡异命名（Mysterious Name）**：函数、变量或类型的名字看不出它做什么、装着什么。→ 重命名；如果起不出一个诚实的名字，说明设计本身就含混。
- **重复代码（Duplicated Code）**：同一个逻辑形状出现在这次变更里不止一个 hunk 或文件中。→ 提取出共享的形状，两处都调用它。
- **依恋情结（Feature Envy）**：一个方法伸进别的对象的数据比伸进自己数据的还多。→ 把这个方法挪到它依恋的数据上。
- **数据泥团（Data Clumps）**：同样几个字段或参数总是结伴出现（一个想要诞生的类型）。→ 把它们捆成一个类型，传这个类型。
- **基本类型偏执（Primitive Obsession）**：用基本类型或字符串顶替一个配得上自己类型的领域概念。→ 给这个概念一个自己的小类型。
- **重复的 switch（Repeated Switches）**：对同一个类型的同一套 `switch`/`if` 级联在变更中反复出现。→ 换成多态，或一张两处共享的映射。
- **霰弹式修改（Shotgun Surgery）**：一次逻辑上的变更迫使 diff 里的许多文件四处散改。→ 把一起变的东西收拢到一个模块里。
- **发散式变化（Divergent Change）**：一个文件或模块因好几个互不相关的原因被修改。→ 拆开，让每个模块只因一个原因而变。
- **夸夸其谈的泛化（Speculative Generality）**：为规格并不存在的需求而添加的抽象、参数或钩子。→ 删掉它；内联回去，直到真实需求出现。
- **消息链（Message Chains）**：调用方不该依赖的长长的 `a.b().c().d()` 导航。→ 在第一个对象上用一个方法把这段导航藏起来。
- **中间人（Middle Man）**：一个基本只是在往下转交的类或函数。→ 砍掉它，直接调用真正的目标。
- **被拒绝的遗赠（Refused Bequest）**：一个忽略或覆盖掉所继承内容大部分的子类或实现者。→ 放弃继承，改用组合。

### 4. 并行孵化两个子智能体

把两个子智能体调用一起发出，在前台运行，然后汇总它们返回的报告。

**标准子智能体的提示词**应包含：

- 完整的 diff 命令和 commit 列表。
- 你在第 3 步找到的标准来源文件清单，**外加第 3 步坏味道基线的完整粘贴**（子智能体没有别的途径拿到它）。
- 简报：“在相关的每个文件/hunk 上报告：(a) diff 违反某条写明标准的每一处：引用该标准（文件 + 规则）；以及 (b) 你发现的任何基线坏味道：点名它并引用 hunk 原文。区分硬性违规与主观判断：违反写明标准可以是硬性的，但基线坏味道永远是主观判断，且仓库写明的标准压过基线。凡是工具强制执行的都跳过。不超过 400 字。”

**规格子智能体的提示词**应包含：

- diff 命令和 commit 列表。
- 规格的路径或取回的内容。
- 简报：“报告：(a) 规格要求了但缺失或不完整的需求；(b) diff 中没人要求的行为（范围蔓延）；(c) 看似已实现、但实现样子不对的需求。每条发现都引用规格的那一行。不超过 400 字。”

如果规格缺失，跳过规格子智能体，并在最终报告中注明这一点。

### 5. 汇总

把两份报告放在 `## Standards` 和 `## Spec` 标题下呈现，原样或只做轻度清理。**不要**合并或重新排序发现，因为两根轴是有意分开的（见“为什么是两根轴”）。

以一行摘要收尾：每根轴的发现总数，以及每根轴内部各自的最严重问题（如果有）。不要跨轴选出一个总赢家：那正是这种分离要防止的重新排序。

## 为什么是两根轴

一个变更可能通过一根轴、却挂掉另一根：

- 遵循了每条标准却实现了错误东西的代码 → **过标准，挂规格。**
- 精确做到 issue 所要求、却破坏项目约定的代码 → **过规格，挂标准。**

分开报告能阻止一根轴把另一根遮住。
