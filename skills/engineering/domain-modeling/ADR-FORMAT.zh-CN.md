# ADR 格式

ADR 存放在 `docs/adr/` 中，使用连续编号：`0001-slug.md`、`0002-slug.md`，以此类推。

按需创建 `docs/adr/` 目录：只有需要第一份 ADR 时才创建。

## 模板

```md
# {决策的简短标题}

{用 1–3 句话说明：背景是什么、我们做出了什么决定，以及为什么。}
```

仅此而已。一份 ADR 可以只有一段话。它的价值在于记录*做出了某项决策这件事*以及*原因*，而不在于填满各个章节。

## 可选部分

只有确实带来价值时才加入这些内容。大多数 ADR 不需要它们。

- **状态** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）：重新审视决策时很有用
- **考虑过的方案**：只有被否决的替代方案值得记住时才需要
- **后果**：只有需要指出不明显的后续影响时才需要

## 编号

扫描 `docs/adr/`，找到现有的最大编号，再加一。

## 何时提议创建 ADR

必须同时满足以下三个条件：

1. **难以逆转**：日后改变主意的成本不可忽视
2. **缺乏背景时会让人意外**：未来的读者看着代码，会疑惑“他们到底为什么要这样做？”
3. **经过真实权衡得出的结果**：确实存在其他可选方案，而你出于具体原因选择了其中一个

如果一项决策容易逆转，就不必记录：到时候直接改就行。如果它并不令人意外，就没人会疑惑原因。如果没有真正的替代方案，除了“我们做了显而易见的事”以外，也没有什么值得记录。

### 哪些决策符合条件

- **架构形态。** “我们使用单体仓库（monorepo）。”“写模型采用事件溯源，读模型投影到 Postgres 中。”
- **上下文之间的集成模式。** “订单处理（Ordering）与计费（Billing）通过领域事件通信，而不是同步 HTTP。”
- **会带来锁定效应的技术选择。** 数据库、消息总线、认证提供商、部署目标。不是每个库都要记录：只记录那些替换起来要花一个季度的选择。
- **边界与范围决策。** “客户数据归客户（Customer）上下文所有；其他上下文只能通过 ID 引用它。”明确说明不做什么，与说明做什么同样有价值。
- **有意偏离显而易见的路径。** “出于 X 原因，我们手写 SQL，而不使用 ORM。”凡是合理的读者会以为应该反过来做的决策，都属于此类。这些记录能防止下一位工程师把刻意为之的设计当作问题来“修复”。
- **代码中看不出来的约束。** “由于合规要求，我们不能使用 AWS。”“由于合作伙伴的 API 合同要求，响应时间必须低于 200ms。”
- **否决理由不明显的替代方案。** 如果你考虑过 GraphQL，却出于一些微妙的原因选择了 REST，就记录下来；否则，半年后又会有人提议使用 GraphQL。
