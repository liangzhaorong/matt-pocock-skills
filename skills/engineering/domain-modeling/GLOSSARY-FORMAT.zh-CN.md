# GLOSSARY.md 格式

## 结构

```md
# {上下文名称}

{用一两句话说明该上下文是什么，以及为什么存在。}

## 用语

**Order（订单）**：
{用一两句话描述该术语}
_避免使用_：Purchase、transaction

**Invoice（发票）**：
交付后发送给客户的付款请求。
_避免使用_：Bill、payment request

**Customer（客户）**：
下订单的个人或组织。
_避免使用_：Client、buyer、account
```

## 规则

- **要有明确主张。** 同一概念有多个词语时，选出最合适的一个，将其余词语列在 `_避免使用_` 下。
- **定义要简练。** 最多一两句话。定义它是什么，而不是它做什么。
- **只包含该项目上下文特有的术语。** 通用编程概念（超时、错误类型、通用工具模式）不属于术语表，即使项目大量使用它们也是如此。添加术语前，先问自己：这是该上下文特有的概念，还是通用编程概念？只有前者才应收录。
- 当术语自然形成若干组时，**用子标题分组**。如果所有术语都属于同一个紧密关联的领域，使用平铺列表即可。

## 单上下文与多上下文仓库

**单上下文（大多数仓库）：** 仓库根目录下放一份 `GLOSSARY.md`。

**多上下文：** 仓库根目录下的 `GLOSSARY-MAP.md` 列出各个上下文、所在位置，以及它们之间的关系：

```md
# 术语表映射

## 上下文

- [订单处理（Ordering）](./src/ordering/GLOSSARY.md)：接收并跟踪客户订单
- [计费（Billing）](./src/billing/GLOSSARY.md)：生成发票并处理付款
- [履约（Fulfillment）](./src/fulfillment/GLOSSARY.md)：管理仓库拣货与发货

## 关系

- **订单处理 → 履约**：订单处理发出 `OrderPlaced` 事件；履约消费这些事件以开始拣货
- **履约 → 计费**：履约发出 `ShipmentDispatched` 事件；计费消费这些事件以生成发票
- **订单处理 ↔ 计费**：共享 `CustomerId` 和 `Money` 类型
```

本技能会推断应采用哪种结构：

- 如果存在 `GLOSSARY-MAP.md`，阅读它以找到各个上下文
- 如果只有根目录的 `GLOSSARY.md`，则为单上下文
- 如果两者都不存在，在第一个术语确定时，按需创建根目录的 `GLOSSARY.md`

存在多个上下文时，推断当前话题与哪个上下文相关。如果不明确，就询问。
