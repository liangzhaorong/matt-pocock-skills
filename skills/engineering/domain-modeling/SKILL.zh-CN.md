# 领域建模

在设计过程中，主动构建并完善项目的领域模型。这是一项*主动*的实践：质疑术语、构造边缘场景，并在术语和决策明确的那一刻将其记录下来。（仅仅为了了解词汇而*阅读* `GLOSSARY.md` 并不属于本技能：那只是任何技能都能用一行指令要求的习惯。本技能适用于你正在改变模型，而不只是使用模型的时候。）

## 文件结构

大多数仓库只有一个上下文：

```
/
├── GLOSSARY.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

如果根目录存在 `GLOSSARY-MAP.md`，说明仓库有多个上下文。该映射文件指明了各个上下文的位置：

```
/
├── GLOSSARY-MAP.md
├── docs/
│   └── adr/                          ← 系统级决策
├── src/
│   ├── ordering/
│   │   ├── GLOSSARY.md
│   │   └── docs/adr/                 ← 特定上下文的决策
│   └── billing/
│       ├── GLOSSARY.md
│       └── docs/adr/
```

按需创建文件：只有确实有内容要写时才创建。如果不存在 `GLOSSARY.md`，就在第一个术语确定时创建。如果不存在 `docs/adr/`，就在需要第一份 ADR 时创建。

## 会话过程中

### 对照术语表提出质疑

当用户使用的术语与 `GLOSSARY.md` 中的现有用语冲突时，立即指出。“你的术语表将‘取消’定义为 X，但你似乎指的是 Y。到底是哪一个？”

### 澄清模糊用语

当用户使用含糊或一词多义的术语时，提出一个精确的规范术语。“你说的‘账户’：是指 Customer 还是 User？它们是不同的概念。”

### 讨论具体场景

讨论领域关系时，用具体场景对其进行压力测试。构造能够探查边缘情况的场景，促使用户明确概念之间的边界。

### 与代码交叉核对

当用户描述某件事如何运作时，检查代码是否与之相符。如果发现矛盾，就指出来：“你的代码会取消整个 Order，但你刚才说可以部分取消。哪个才是正确的？”

### 即时更新 GLOSSARY.md

术语一旦确定，就立即更新 `GLOSSARY.md`。不要攒起来批量处理：确定一个就记录一个。使用 [GLOSSARY-FORMAT.md](./GLOSSARY-FORMAT.md) 中的格式。

`GLOSSARY.md` 应完全不含实现细节。不要将 `GLOSSARY.md` 当作规格文档、草稿本或实现决策的存放处。它只是术语表，除此之外别无他用。

### 谨慎提议创建 ADR

只有同时满足以下三个条件时，才提议创建 ADR：

1. **难以逆转**：日后改变主意的成本不可忽视
2. **缺乏背景时会让人意外**：未来的读者会疑惑“为什么要这样做？”
3. **经过真实权衡得出的结果**：确实存在其他可选方案，而你出于具体原因选择了其中一个

缺少任何一个条件，就不写 ADR。使用 [ADR-FORMAT.md](./ADR-FORMAT.md) 中的格式。
