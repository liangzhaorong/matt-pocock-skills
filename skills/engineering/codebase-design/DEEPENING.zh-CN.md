# 深化

如何根据一组浅模块的依赖，安全地将它们深化。本文沿用 [SKILL.md](SKILL.md) 中的术语：**模块**、**接口**、**接缝**、**适配器**。

## 依赖分类

评估一个候选深化对象时，先对它的依赖进行分类。依赖类别决定了如何跨越接缝测试深化后的模块。

### 1. 进程内依赖

纯计算、内存中的状态，没有 I/O。始终可以深化：合并这些模块，直接通过新接口进行测试。无需适配器。

### 2. 可在本地替代的依赖

具有本地测试替代品的依赖（例如用 PGLite 替代 Postgres，或使用内存文件系统）。只要存在替代品，就可以深化。测试深化后的模块时，在测试套件中运行该替代品。接缝位于内部；模块的外部接口上不设置端口。

### 3. 远程但由自己掌控的依赖（端口与适配器）

跨越网络边界的自有服务（微服务、内部 API）。在接缝处定义一个**端口**（接口）。深模块负责逻辑；传输机制以**适配器**的形式注入。测试使用内存适配器。生产环境使用 HTTP/gRPC/队列适配器。

建议表述：*“在接缝处定义一个端口，为生产环境实现 HTTP 适配器，为测试实现内存适配器，这样即使部署跨越网络，逻辑仍集中在一个深模块中。”*

### 4. 真正的外部依赖（Mock）

你无法控制的第三方服务（Stripe、Twilio 等）。深化后的模块通过注入的端口接收外部依赖；测试提供 mock 适配器。

## 接缝纪律

- **一个适配器意味着一条假想的接缝，两个适配器才意味着一条真实的接缝。** 除非至少两个适配器都有存在的理由（通常是生产环境适配器和测试适配器），否则不要引入端口。只有一个适配器的接缝只增加了一层间接性。
- **内部接缝与外部接缝。** 深模块除了接口处的外部接缝，还可以有内部接缝（实现私有，供模块自身的测试使用）。不要仅仅因为测试需要使用内部接缝，就通过接口将其暴露出来。

## 测试策略：替换，而非叠加

- 一旦有了针对深化后模块接口的测试，原先针对浅模块的单元测试就变得多余；将其删除。
- 针对深化后模块的接口编写新测试。**接口就是测试面**。
- 测试应通过接口对可观察的结果进行断言，而不是对内部状态进行断言。
- 内部重构后，测试应仍然有效，因为它们描述的是行为，而不是实现。如果实现一变，测试就必须跟着变，说明它测试的内容越过了接口，深入到了实现内部。
