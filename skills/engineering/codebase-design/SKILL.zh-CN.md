# 代码库设计

设计**深模块**：小接口背后藏大量行为，安放在一条干净的接缝上，可通过该接口测试。凡在设计或重构代码之处，都用这套语言和这些原则。目标是给调用方杠杆、给维护者局部性、给所有人可测试性。

## 词汇表

精确使用这些术语：不要用“组件”“服务”“API”或“边界”来顶替。语言一致就是全部意义所在。

**模块（Module）**：任何有接口和实现的东西。刻意不区分规模：一个函数、一个类、一个包、一段跨层的切片。*避免使用*：unit、component、service。

**接口（Interface）**：调用方要正确使用该模块所必须知道的一切：类型签名，还包括不变量、顺序约束、错误模式、必需配置和性能特征。*避免使用*：API、signature（都太窄，只指类型层面的表面）。

**实现（Implementation）**：模块里面是什么，它的代码主体。区别于**适配器（Adapter）**：一个东西可以是小适配器配大实现（Postgres 仓库），也可以是大适配器配小实现（内存假实现）。话题是接缝时选用“适配器”，其余时候用“实现”。

**深度（Depth）**：接口处的杠杆。调用方（或测试）每学一个单位的接口，能驱动多少行为。小接口背后坐着大量行为时，模块是**深**的；接口几乎和实现一样复杂时，是**浅**的。

**接缝（Seam）**（Michael Feathers）：一个不用就地编辑就能改变行为的地方；模块接口所在的*位置*。接缝放哪里是一个独立的设计决定，区别于它背后放什么。*避免使用*：boundary（与 DDD 的限界上下文撞义）。

**适配器（Adapter）**：在接缝处满足某个接口的具体之物。它描述的是*角色*（填的是哪个槽位），不是内容（里面装着什么）。

**杠杆（Leverage）**：调用方从深度中得到的东西：每学一个单位的接口换来更多能力。一份实现跨 N 个调用点和 M 个测试回本。

**局部性（Locality）**：维护者从深度中得到的东西：变更、bug、知识和验证集中在一个地方，而不是摊到各个调用方身上。修一次，处处都修好。

## 深与浅

**深模块** = 小接口 + 大量实现：

```
┌─────────────────────┐
│       小接口        │  ← 方法少，参数简单
├─────────────────────┤
│                     │
│       深实现        │  ← 复杂逻辑被藏起来
│                     │
└─────────────────────┘
```

**浅模块** = 大接口 + 少量实现（要避免）：

```
┌─────────────────────────────────┐
│             大接口              │  ← 方法多，参数复杂
├─────────────────────────────────┤
│             薄实现              │  ← 只是透传
└─────────────────────────────────┘
```

设计接口时，问自己：

- 我能不能减少方法数量？
- 我能不能简化参数？
- 我能不能把更多复杂度藏进里面？

## 原则

- **深度是接口的属性，不是实现的属性。**深模块内部可以由小的、可 mock、可替换的部件组成；只是它们不属于接口。一个模块除接口处的**外部接缝**外，还可以有**内部接缝**（为实现私有，供它自己的测试使用）。
- **删除测试。**想象删掉这个模块。如果复杂度随之消失，它原来只是个传声筒。如果复杂度在 N 个调用方身上重新出现，说明它配得上自己的位置。
- **接口就是测试面。**调用方和测试穿过同一条接缝。如果你想测到接口*背后*去，这个模块的形状多半是错的。
- **一个适配器意味着一条假想的接缝，两个适配器才意味着一条真的。**除非真有什么东西在接缝两侧变化，否则别引入接缝。

## 为可测试性而设计

好的接口让测试变得自然：

1. **接受依赖，不要创造依赖。**

   ```typescript
   // 可测试
   function processOrder(order, paymentGateway) {}

   // 难测试
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **返回结果，不要产生副作用。**

   ```typescript
   // 可测试
   function calculateDiscount(cart): Discount {}

   // 难测试
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **小的表面积。**方法更少 = 所需测试更少。参数更少 = 测试准备更简单。

## 关系

- 一个**模块**恰好有一个**接口**（它呈现给调用方和测试的那张表面）。
- **深度**是**模块**的属性，以它的**接口**为尺度衡量。
- **接缝**是**模块**的**接口**所在之处。
- **适配器**坐在**接缝**上，满足那个**接口**。
- **深度**为调用方产出**杠杆**，为维护者产出**局部性**。

## 拒绝采用的定义

- **把深度定义为实现行数与接口行数之比**（Ousterhout 的定义）：这会奖励往实现里注水。我们改用“深度即杠杆”。
- **把“接口”当作 TypeScript 的 `interface` 关键字或一个类的公开方法**：太窄了：这里的接口包括调用方必须知道的每一个事实。
- **“边界（boundary）”**：与 DDD 的限界上下文撞义。要说**接缝**或**接口**。
