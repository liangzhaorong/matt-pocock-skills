一个粗略的想法来了：它大到单个代理会话装不下，而且裹在迷雾里：从这里到**目的地**的路还看不见。探路（wayfinding）讲的是找到这条路，而不是朝目的地猛冲。本技能把这条路绘制成仓库 issue 跟踪器上的一张**共享地图**，然后逐一处理它的**决策工单**（那些"解决本身就是一个决策"的问题，而不是待执行的建筑切片），直到路线清晰为止。

目的地因每次行动（effort）而异，为它命名是绘图的第一个动作：它塑造每一张工单。目的地可能是一份用来交接和迭代的规格，可能是一个在规划开始前就要锁定的决策，也可能是一次就地完成的变更，比如数据结构迁移。这张地图与领域无关：工程工作、课程内容，任何符合这个形状的东西都行。

## 只规划，不执行

Wayfinder 默认是**规划**：每张工单解决一个决策，而当路已清晰、在有人去实际动手之前再无悬而未决之事时，地图就完成了。想要直接动手把活干了的冲动，通常正是你已到达地图边缘、该交接出去的信号。一次行动可以在其**备注**中覆盖这一默认，把执行也纳入地图本身；但若没有这种约定，产出的是决策，而不是交付物。

## 以名称相称

每张地图和每张工单都是一个 issue，因此都有一个**名字**：它的标题。在人读到的所有内容里（叙述文字、地图的"已有决策"），都用这个名字来指代它，绝不用裸的 id、编号或 slug。一排 `#42, #43, #44` 无法卒读；名字则一眼可辨。id 和 URL 并不会消失：名字裹着它的链接，id 和 URL 只是随名字附带在*里面*，绝不能顶替名字。

## 地图

地图是本仓库 issue 跟踪器上的一个单独 issue，带 `wayfinder:map` 标签，是权威工件（canonical artifact）。它的工单是该地图的子 issue。

地图是**索引**，不是存储。它列出已做出的决策，并指向承载其细节的工单；一个决策只活在一个地方，即它的工单，因此地图从不复述决策，只给出摘要并附链接。

**地图、其子工单、阻塞关系以及前沿查询实际存放在哪里，取决于具体的跟踪器。** issue 跟踪器本应已提供给你。如果没有，请让用户运行 `/setup-matt-pocock-skills`。查阅跟踪器文档的 "Wayfinding operations" 一节，了解*本*仓库如何表达这些概念。如果确实没有提供跟踪器，默认使用 local-markdown 跟踪器。

### 地图正文

整张地图的低分辨率视图，每个会话加载一次。开放中的工单**不**在此列出：它们是开放中的子 issue，通过查询获取。

```markdown
## 目的地（Destination）

<到达这张地图尽头是什么样子：这次行动要探到的规格、决策或变更。一两行；
每个会话在挑选工单之前先以它定向。>

## 备注（Notes）

<领域；每个会话都应查阅的技能；本次行动的长期偏好>

## 已有决策（Decisions so far）

<!-- 索引：每张已关闭的工单一行，足以判断相关性即可，
细节通过链接放大到工单里去看 -->

- [<已关闭工单的标题>](链接): <答案的一行摘要>

## 尚未明确（Not yet specified）

<!-- 见"战争迷雾"：范围内但还开不成工单的迷雾；随前沿推进而毕业为工单 -->

## 范围外（Out of scope）

<!-- 见"范围外"：已被判定在目的地之外的工作；关闭，永不毕业 -->
```

### 工单

每张工单都是地图的**子 issue**；以跟踪器的 issue id 为其身份。它的正文就是问题本身，体量控制在一个 10 万（100K）token 的代理会话内：

```markdown
## 问题（Question）

<这张工单要解决的决策或调查>
```

每张工单带一个 `wayfinder:<type>` 标签，取值为 `research`、`prototype`、`grilling`、`task` 之一（见[工单类型](#ticket-types)）。`wayfinder:` 标签是地图及其工单所携带的唯一标签，绝不带 `ready-for-agent` 这类分诊标签：它们是决策，不是实现工作。

会话通过把工单指派给推动这张地图的开发者来**认领**它，而且**先**做这件事，先于任何工作，这样并发会话就会跳过它。这个指派人*就是*认领标志：一张开放中且无人指派的工单就是未被认领的。

阻塞使用跟踪器的**原生**依赖关系：这一点至关重要，因为它能在跟踪器自己的 UI 里*可视化地*呈现前沿，人不打开地图就能看到什么可以下手。只有缺乏原生阻塞能力的跟踪器才退回正文约定。当所有阻塞某工单的工单都已关闭时，该工单就是**已解除阻塞**的；**前沿（frontier）**是那些开放中、未阻塞、未认领的子工单，即已知世界的边缘。

答案不属于正文；它在解决时才记录（见[沿地图推进](#work-through-the-map)）。解决工单过程中产出的资产从 issue 链接过去，而不是粘贴进来。

## 工单类型（Ticket Types）

每张工单要么是 **HITL**（human in the loop，人在环：与一位能代表自己发言的人*一起*完成），要么是 **AFK**（无人值守），由代理独自推进。HITL 工单只能通过这种实时交流来解决；代理绝不替人顶下人的那一半（一个自问自答的拷问代理就已经破坏了这一点）。

- **Research（调研）**（AFK）：阅读文档、第三方 API 或知识库等本地资源，把某个决策正在等待的事实挖出来。由一个调用 Skill 工具并传入 "research" 的子代理解决。当需要当前工作目录之外的知识时使用。
- **Prototype（原型）**（HITL）：通过调用 Skill 工具传入 "prototype"，制作一个廉价、粗糙、可供人做出反应的具体产物（一份大纲、一个粗稿、一个桩，或 UI/逻辑代码），来提高讨论的保真度。原型作为资产链接在工单上。当"它应该长什么样"或"它应该有怎样的行为"是关键问题时使用。
- **Grilling（拷问）**（HITL）：对话。默认情形。始终调用两次 Skill 工具，分别传入 "grilling" 和 "domain-modeling"。
- **Task（任务）**（HITL 或 AFK）：必须在做出某个*决策*之前完成的体力活：没有东西可决策、可原型、可调研，但在它完成之前讨论一直被卡着。比如注册一个服务好让它的 API 能被评判、开通权限、搬移数据好让它的形状能被看见。这是唯一一种"动手做"而非"做决策"的类型，它靠解除某个决策的阻塞来赢得自己的位置，而不是靠交付目的地。凡是代理能独自完成的就独自推进（AFK）；否则它交给人类一份精确的清单（HITL）。工作完成即视为解决；答案要记录做了什么，以及后续工单会依赖的、由此产生的事实（凭据位置、新 URL、行数）。

## 战争迷雾（Fog of War）

地图*有意*保持不完整：还看不见的东西就不要画。在存活工单之外是**战争迷雾**：那些你料得到正在逼近、却还无法钉死的决策与调查的模糊图景，因为它们悬在仍然开放的问题上。解决一张工单会拨开它前方的迷雾，把此刻已能明确描述的东西一张一张毕业成新工单，直到通往目的地的路清晰可见、再无工单剩下。

地图的**"尚未明确"**部分就是写下这层模糊图景的地方：疑似存在的问题、日后要再回访的区域。它是通往目的地方向上尚未发现的前沿：这里的一切都在范围内，只是还没清晰到可以开成工单。视图允许你写多粗就写多粗、多细就多细；它同时还是给协作者的路标，让人读出这次行动正走向哪里。

**迷雾还是工单？** 判断标准是你现在能否把问题陈述得足够精确，而*不是*你现在能否回答它。

- 当问题已经足够清晰锐利时，开**工单**，哪怕它被阻塞、暂时无法行动。
- 当你还无法把问题表述得那么锐利时，记入**"尚未明确"**。不要预先把迷雾切成工单大小的碎块：它的颗粒比工单粗，一片迷雾在前沿抵达时可能毕业成好几张工单，也可能一张都没有。

**"尚未明确"**不含已经决定了的东西（已有决策）、已经是存活工单的东西，以及范围外的东西（见下一节）。

## 范围外（Out of Scope）

迷雾只会朝*目的地*方向聚集。目的地圈定了范围，因此位于它之外的工作是**范围外**的：它不是迷雾，也不属于**"尚未明确"**。它在地图上有自己独立的**"范围外"**部分：那些你有意识地排除在*这次*行动之外的工作。让东西落进这里的是范围，而不是清晰度。

范围外的工作永远不会毕业（前沿止步于目的地），因此只有当目的地被重新划定，它才会回来，而且是以一次全新行动的形式回来，不是恢复旧行动。

把某件事划为范围外是一次范围裁定，不是路线上的一步。当一张已存在的工单被发现其实位于目的地之外（绘图时误圈进来的，或被某次解决暴露出来的），**关闭它**（关闭的工单明确不在前沿上），并在**"范围外"**部分留下一行：摘要加上它为什么在范围外，并链接那张已关闭的工单。它不进入**"已有决策"**，那一节记录的是实际走过的路线；范围边界不是路线上的一步。

## 调用

两种模式。无论哪种，**每个会话绝不要解决超过一张工单**，research 工单是唯一例外。

### 绘制地图

用户带着一个粗略的想法调用。

1. **为目的地命名。** 调用两次 Skill 工具，分别传入 "grilling" 和 "domain-modeling"，钉死这张地图要探向何处：那份规格、那个决策，或那次变更。目的地圈定范围，因此最先敲定它。
2. **测绘前沿。** 再次拷问，这次**广度优先**：在整个空间上铺开，而不是在任何一条线索上深挖，把开放中的决策和现在就能迈出的头几步都挖出来。**如果这轮没有翻出任何迷雾**（通往目的地的路已经清晰，整个旅程小到一个会话装得下），你就不需要地图。停下来问用户想怎么继续。
3. **创建地图**（打 `wayfinder:map` 标签）：填好目的地和备注，"已有决策"留空，把迷雾草绘进**"尚未明确"**。
4. **把现在就能明确描述的工单**创建为地图的子 issue，然后在**第二遍**里连好阻塞边（issue 有了 id 才能互相引用）。交叉引用也在这一遍里写，用真实的 id：占位符 `#<n>` 会自动链接到不相干的 issue。连线把它们分进前沿和被阻塞两组；一切还不能明确描述的东西留在迷雾里：即**"尚未明确"**部分。
5. **发射调研子代理。** 为你刚创建的每张 `research` 工单启动一个带全新上下文窗口的子代理，让它调用 Skill 工具传入 "research" 来并行解决，把发现记录到一个一次性的 `research/<name>` 分支上，并从工单留下一个指向它的上下文指针。推送该分支但不开 PR：它永远不会被合并。
6. 停下：绘图是一个会话的活；它不亲手解决任何工单。

### 沿地图推进

用户带着一张地图（URL 或编号）调用。指定工单是**可选的**：没有指定时，由你来挑下一个决策，而不是用户。

1. 加载**地图**：低分辨率视图，而不是每张工单的正文。
2. 选择工单。如果用户点名了某张，就用它。否则按顺序取第一张前沿工单。**认领它**：在任何工作之前先把它指派给自己。
3. 按其 `wayfinder:<type>` 标签所指定的类型来解决它（见[工单类型](#ticket-types)）。读标签，而不只是正文：正文从不写明类型。**按需放大**：按需拉取任何相关工单或已关闭工单的完整正文；`## Notes` 块点名了哪些技能，就调用 Skill 工具加载哪些。拿不准时，调用两次 Skill 工具，分别传入 "grilling" 和 "domain-modeling"。
4. 记录解决结果：把答案作为一条**结案评论**发布，**关闭**该 issue，并向地图的"已有决策"**追加一条上下文指针**。
5. 补上新翻出来的工单（先创建、后连线）；把答案已使其变得可明确描述的迷雾毕业成工单，并把每片已毕业的迷雾从**"尚未明确"**中清掉，让它只以新工单的形式存在。如果答案揭示某张工单（本张或他张）位于目的地之外，**把它划为范围外**，而不是在路线上解决它。如果该决策使地图的其他部分失效，更新或删除那些工单。

用户可能并行推进多张未阻塞的工单，因此要预料到其他会话正在并发编辑跟踪器。
