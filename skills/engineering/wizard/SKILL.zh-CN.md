# 向导（Wizard）

**向导（wizard）**是一个 bash 脚本，带领人类一步步完成一个手工过程：这种过程手工做很繁琐，每次重新向 AI 解释一遍同样很繁琐。它打开每个 URL，明确说出点什么、复制什么，捕获这些值，把它们写到该去的地方（`.env`、GitHub secrets），每个阶段都做确认，并显示还剩几个阶段。它可能用于配置第三方服务、执行一次性迁移，或把项目从一个状态搬到另一个状态。

愉悦的 UX 已经由 [template.sh](template.sh) 解决：逐阶段的进度、确认闸门、跨平台打开 URL（包括 WSL）、机密信息的隐藏输入、幂等的 `.env` upsert（存在即更新、不存在即插入）、`gh secret`/`gh variable` 写入，以及收尾摘要。**你的工作只是划定过程范围并编写各个阶段。** `STAGES` 标记之上的库代码在每个向导中都完全相同；这种一致性正是要点所在：绝不要手改它。

向导默认是一次性的：为一次运行而构建，保存到一个临时（scratch）目录或 `scripts/` 路径，任务完成即删除。只有当用户想要一条可重复、应当留在仓库里的设置路径时才提交它。

## 流程

### 1. 划定过程范围

列出人类必须执行的每一个手工步骤，以及沿途捕获的每一个值。先读仓库，别一上来就问：

- 设置类：`.env`、`.env.example`、`.env.*`、`README`、`docker-compose*`、框架配置，以及 `.github/workflows/*`（每一处 `secrets.*` / `vars.*` 引用都是向导必须产出的值）。
- 迁移或过渡类：当前状态、目标状态，以及两者之间的不可逆动作。

然后向用户展示按顺序排列的阶段列表及各阶段产出的值，并确认：用户可能会增加、删除或重排阶段。

**完成标准：** 每个阶段都按顺序命名，且对每个被捕获的值你都清楚：(a) 人类从哪里拿到它，(b) 它被写到哪里（`.env`、GitHub secret、两者都写，或哪儿都不写；有些阶段是纯动作），(c) 它是机密的（隐藏输入）还是公开的。

### 2. 规划每个阶段的旅程

对每个阶段，写出人类要走的精确路径：打开哪个 URL、在那里做什么、值显示在何处、它填入哪个变量：例如 "Dashboard → Developers → API keys → Reveal test key → 复制"。在你确实不了解当前 UI 或确切命令的地方，直说出来，询问用户或查文档：绝不编造可能不存在的步骤。

**完成标准：** 每个阶段都能落成陌生人也能照做的具体指令。

### 3. 编写向导

把 `template.sh` 复制到目标路径。把示例阶段替换为每个步骤一个 `stage`，按依赖顺序排列。使用库里的辅助函数：`stage`、`say`/`step`、`open_url`、`ask`/`ask_secret`、`write_env`、`set_secret`/`set_var`、`pause`/`confirm`。把 `TOTAL_STAGES` 设为你所写阶段的数量。

守住模板立下的标准：先打开 URL 再索要它的值；任何机密的东西都用 `ask_secret`；每个要持久化的值都 `write_env`；只对 CI 真正需要的值 `set_secret`；任何不可逆动作之前先 `confirm`。每个 `stage` 都会清屏，只显示当前步骤：把一个阶段控制在单一专注的任务上，人类需要的信息就不会被滚出屏幕。不要动标记之上的库代码。

### 4. 验证并交接

- `bash -n <script>`；有 `shellcheck` 就跑一遍。
- `chmod +x <script>`。
- 不要自己端到端运行它：它会打开浏览器并阻塞等待人类输入。改为静态走查：步骤 1 中的每个值都被捕获，并落到步骤 1 所说的位置；每个 `set_secret` 的名字都与 CI 中某处 `secrets.*` 引用精确对应。
- 告诉用户如何运行它。如果这是一条可重复的设置路径，提交它并从 README 链接它，让下一个人直接运行脚本，而不是去问 AI。
