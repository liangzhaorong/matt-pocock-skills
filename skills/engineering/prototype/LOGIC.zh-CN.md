# 逻辑原型

一个自包含的 HTML 文件（一份**可分享的演示**），让任何人都能通过点击按钮驱动状态模型。当问题涉及**业务逻辑、状态转换或数据结构**时，使用这种形式：这些东西在纸面上看似合理，但只有放进真实案例中运行，才会感觉到哪里不对。

因为只有一个文件，无需安装任何东西，你可以把它交给非开发人员（设计师、产品经理、领域专家），让他们亲自体验模型。因此，它使用他们的语言，而不是代码的语言。

## 何时适合这种形式

- “我不确定这个状态机能否处理先发生 X 再发生 Y 的边缘情况。”
- “这个数据模型真的能表达这样的情况吗……”
- “我想在编写 API 之前，先摸索一下它应该是什么样。”
- 任何想要**按按钮、观察状态变化**的情况。

如果问题是“它应该是什么样子”，就不该选择这个分支。使用 [UI.md](UI.md)。

## 流程

### 1. 明确问题

写代码之前，先写清楚原型要探索什么状态模型、回答什么问题。用一段话放在演示顶部（作为可见的介绍，而不只是注释）。回答错问题的逻辑原型纯属浪费，因此要把问题明确写出来，以便之后核对，不论用户现在正在看，还是离开后再回来。

### 2. 将逻辑隔离在可移植的模块中

将实际逻辑（回答问题的那部分）放在单个 `<script>` 块中，写成一个小型纯模块，以便之后能直接取出，放入真正的代码库中。周围的页面是一次性的；这个模块不是。

合适的形式取决于问题：

- **纯 reducer**：`(state, action) => state`。适用于操作是离散事件、状态是单个值的情况。
- **状态机**：显式定义状态与转换。适用于“当前究竟允许哪些操作”也是问题一部分的情况。
- **针对普通数据类型的一小组纯函数**。适用于没有隐含的当前状态、只有数据转换的情况。
- 当逻辑确实持续维护内部状态时，使用**具有清晰方法接口的类或模块**。

选择最适合所问问题的形式，*而不是*最容易接到页面上的形式。保持纯粹：不涉及 DOM，不引用 `document`，按钮处理函数也不应伸入模块内部。页面调用模块；反方向不应有任何调用。这使原型在完成使命后仍有用处：问题得到回答后，经过验证的 reducer / 状态机 / 函数组可以独立移入实际模块。

### 3. 构建可分享的 HTML 文件

一个文件，使用原生 HTML/CSS/JS：无框架、无打包器、无服务器，所有内容内联，双击即可打开，通过邮件传来传去也仍能使用。任何人打开它就应该能运行。

面向非开发人员编写。每个标签都使用**领域语言**，而不是代码：按钮和状态要像业务描述，而不是 reducer。用通俗的话解释正在发生什么。

从上到下，按清晰的层次布局：

1. **标题和一句话说明**：说明这个演示可以探索什么（即步骤 1 中的问题）。
2. **当前状态**：将完整的相关状态渲染为可读面板（带标签的字段，而非原始 JSON 转储），每次点击后重新渲染，让变化可见。如果有助于非开发人员理解，就指出刚刚发生了什么变化。
3. **自由操作按钮**：每个操作对应一个按钮，始终可用，使任何人都能按任意顺序试探模型。每次点击都会派发相应操作并重新渲染状态。
4. **引导演练**：一组**场景**，每个场景一个标签页。每个标签页包含一段简短、通俗的场景说明（它设置了什么情境、需要观察什么），下方按顺序列出该场景中**需要按的按钮**。每一步都是一个真实按钮：点击后执行该操作，并进入下一步。开始演练时重置到已知的初始状态，确保每次场景运行方式一致。

选择能够展示棘手情况的场景，也就是那些难以在纸面上推演的情况：正常路径、棘手的边缘情况、尝试执行本不该允许的操作。

保持美观而克制：清晰的排版、充足的间距、一种强调色。不加动画，不搞花招：不要让任何东西抢走状态和按钮的注意力。

### 4. 交给用户

将文件发给用户，或为他们打开。用户有空时会点击演练、自由操作；有价值的时刻是他们说“等等，这不应该被允许”或“咦，我以为 X 会不一样”。这些就是*想法*中的 bug，也正是原型的全部意义。如果他们想要新操作或新场景，就加上。原型会不断演进。

### 5. 留存答案与原型

原型回答了问题之后，先记录答案，再按 [SKILL](SKILL.md) 描述的方式留存原型。对于逻辑原型，具体对应如下：经过验证的 reducer / 状态机 / 函数组移入实际模块（即决策已融入代码）；HTML 外壳随原型一同保存在专门留存一次性原型的分支上，作为一手资料。由于它是一个自包含文件，在该分支上重新运行仍然极其简单。

## 反模式

- **不要添加测试。** 需要测试的原型已经不再是原型。
- **不要连接真正的数据库。** 除非问题专门涉及持久化，否则使用内存状态。
- **不要泛化。** 不考虑“如果我们以后想支持 X 呢”。原型只回答一个问题。
- **不要把逻辑与页面混在一起。** 如果纯模块引用了 DOM、`document` 或按钮处理函数，就无法再直接移用了。让页面保持为纯模块之上的一层薄壳。
- **不要使用框架、打包器或服务器。** 只需一个接收者双击即可打开的文件；React 应用或开发服务器会破坏“可分享”这一特性。
- **不要将 HTML 外壳发布到生产环境。** 页面针对人工逐步点击操作做了优化。背后的逻辑模块才是值得保留的部分。
