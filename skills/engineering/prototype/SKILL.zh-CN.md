# 原型

原型是**用来回答一个问题的一次性代码**。问题决定原型的形式。

## 选择分支

根据用户的提示、周围的代码，或在用户在场时询问，确定要回答的是哪个问题：

- **“这个逻辑 / 状态模型是否合理？”** → [LOGIC.md](LOGIC.md)。构建一个可分享的 HTML 文件（自由操作按钮，加上按标签页组织的引导演练），让状态机经历那些在纸面上难以推演的情况，并让非开发人员也能操作。
- **“它应该是什么样子？”** → [UI.md](UI.md)。在同一路由上生成几个截然不同的 UI 变体，通过 URL 查询参数和底部悬浮栏切换。

这两个分支的产物截然不同，因此选错分支会让整个原型白做。如果问题确实含糊，而又联系不上用户，就默认选择与周围代码更匹配的分支（后端模块 → 逻辑；页面或组件 → UI），并在原型顶部说明这一假设。

## 两个分支共同适用的规则

1. **从第一天起就按一次性代码对待，并明确标注。** 将原型代码放在实际使用位置附近（紧挨着它所探索的模块或页面），使上下文一目了然，但命名要让随手浏览的人也能看出这是原型，而非生产代码。对于一次性 UI 路由，遵循项目现有的路由约定；不要另创顶层结构。
2. **运行极其简单。** UI 原型通过项目任务运行器中的一条命令启动：`pnpm <name>`、`python <path>`、`bun <path>` 等。逻辑演示则是一个用户双击即可打开的 HTML 文件。无论哪种方式，启动都不需要费脑筋。
3. **默认不持久化。** 状态存放在内存中。持久化应是原型要*检验*的对象，而不是原型所依赖的东西。如果问题明确涉及数据库，就使用临时数据库或本地文件，并用清楚表达“原型，可以清空”的名称标记。
4. **跳过打磨。** 不写测试，不添加超出确保原型*可运行*所需范围的错误处理，不做抽象。目的是快速获得认识。
5. **让状态可见。** 每次操作后（逻辑），或每次切换变体时（UI），输出或渲染完整的相关状态，让用户看到发生了什么变化。
6. **完成后留存。** 将任何经过验证的决策融入实际代码，再将原型本身作为**一手资料**留存：提交到一个用于保存一次性原型的分支，不进入 main，并在实现工单中留下指向该分支的上下文指针。也要在工单或提交中记录答案（结论，以及它解决了什么问题）。主分支只保留经过验证的决策。
