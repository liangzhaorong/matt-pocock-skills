# UI 原型

在同一路由上生成**几个截然不同的 UI 变体**，通过底部悬浮栏切换。用户在浏览器中切换变体，选定一个（或从各个变体中取用部分设计），然后丢弃其余部分。

如果问题关乎逻辑或状态，而不是外观，就不该选择这个分支。使用 [LOGIC.md](LOGIC.md)。

## 何时适合这种形式

- “这个页面应该是什么样子？”
- “在决定之前，我想先看看这个仪表盘的几个方案。”
- “给设置页面试一种不同的布局。”
- 任何用户否则就会花上一整天，在脑中三个模糊草图之间犹豫的情况。

## 两种子形式：强烈优先选择子形式 A

当 UI 原型**与应用的其余部分放在一起**时，会容易判断得多：真实的页首、真实的侧栏、真实的数据、真实的信息密度。独立的一次性路由则像处于真空中：每个变体孤立来看都不错。只要有合适的现有页面承载这些变体，就默认选择子形式 A。只有原型确实没有合适的现有页面可放时，才选择子形式 B。

### 子形式 A：调整现有页面（首选）

路由已经存在。变体在**同一路由上**渲染，通过 `?variant=` URL 查询参数控制。现有的数据获取、参数和认证全部保留。只替换渲染部分。这是默认选择；除非有明确理由，否则就选它。

如果原型所探索的内容还没有自己的页面，但*自然应当位于某个页面内部*（仪表盘的新区域、设置页面的新卡片、现有流程中的新步骤），仍然属于子形式 A。将变体挂载在承载它们的页面内部。

### 子形式 B：新页面（最后手段）

只有所探索的内容确实没有可供容纳的现有页面时，才使用这种形式（例如全新的顶层界面，或无法合理嵌入任何地方的流程）。

按照项目现有的路由约定创建一个**一次性路由**。不要另创顶层结构。命名要让人一眼看出这是原型（例如在路径或文件名中包含 `prototype` 一词）。同样使用 `?variant=` 模式。

在决定采用子形式 B 之前，先核实：真的没有现有页面可以嵌入吗？空路由会掩盖那些在已有内容的路由中会暴露的设计问题。

两种子形式使用完全相同的底部悬浮栏。

## 流程

### 1. 明确问题并选定 N

默认生成 **3 个变体**。超过 5 个后，就不再是截然不同的方案，而开始成为噪声，因此最多 5 个。

在原型所在位置或文件顶部注释中，用一行写明计划：

> “在现有 `/settings` 路由上提供设置页面的三个变体，通过 `?variant=` 切换。”

无论用户是否在场提出异议，这种做法都适用。

### 2. 生成截然不同的变体

起草每个变体。每个变体都必须符合以下要求：

- 页面的用途，以及它能够访问的数据。
- 项目的组件库 / 样式系统（TailwindCSS、shadcn、MUI、原生 CSS 等）。
- 清晰的导出组件名称，例如 `VariantA`、`VariantB`、`VariantC`。

变体必须在**结构上不同**：布局不同、信息层级不同、主要操作方式不同，而不只是颜色不同。三个略微调整的卡片网格不是 UI 原型，只是壁纸。如果两份草稿过于相似，就以“不要使用卡片网格”为明确要求，重做其中一个。

### 3. 将它们连接起来

在路由上创建一个统一的切换器组件：

```tsx
// 伪代码，请根据项目框架调整
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

对于子形式 A（现有页面）：保留切换器上方所有现有的数据获取逻辑；只有渲染的子树随变体变化。

对于子形式 B（新页面）：在 `/prototype/<name>` 下的一次性路由中挂载同一个切换器。

### 4. 构建悬浮切换器

一个固定在屏幕底部中央的小栏，包含三部分：

- **左箭头**：切换到上一个变体（循环切换）。
- **变体标签**：显示当前变体的标识；如果变体导出了名称，也显示该名称。例如 `B (Sidebar layout)`。
- **右箭头**：切换到下一个变体（循环切换）。

行为：

- 点击箭头时更新 URL 查询参数（使用框架的路由器，例如 Next 的 `router.replace`、React Router 的 `navigate` 等），使变体可以分享，且重新加载后保持不变。
- 键盘：`←` 和 `→` 方向键也可以循环切换。当焦点位于 `<input>`、`<textarea>` 或 `[contenteditable]` 上时，不要拦截方向键。
- 视觉上与页面明显区分（例如高对比度胶囊形状、轻微阴影），让人一眼看出它不是正在评估的设计的一部分。
- 在生产构建中隐藏：使用 `process.env.NODE_ENV !== 'production'` 或等效检查进行控制，防止意外合并原型时将切换栏发布给用户。

将切换器放在一个共享组件中，使两种子形式都能复用。放置位置遵循项目中共享 UI 的现有组织方式。

### 5. 交给用户

告知 URL（以及 `?variant=` 的各个取值）。用户有空时会自行切换查看。有价值的反馈通常是**“我想要 B 的页首，加上 C 的侧栏”**，那才是他们真正想要的设计。

### 6. 留存答案并清理

某个变体胜出后，记录答案（选中了哪个变体，以及原因），再按 [SKILL](SKILL.md) 描述的方式留存原型。将胜出的方案融入实际代码，将其余部分移入专门留存一次性原型的分支，而不是 main：

- **子形式 A**：将胜出的方案融入现有页面；从 main 中移除未选中的变体和切换器。
- **子形式 B**：将胜出的变体转为正式路由；从 main 中移除一次性路由和切换器。

完整的变体集合是一手资料，因此应进入专门留存一次性原型的分支，而不是垃圾桶；变体组件和切换器如果留在主分支，会很快过时，并让后续读者困惑。

## 反模式

- **变体仅在颜色或文案上不同。** 那只是微调，不是原型。真正的变体在结构上有不同主张。
- **变体之间共享过多代码。** 共享一个 `<Header>` 没问题；共享一个 `<Layout>` 就违背了目的。每个变体都应该能自由地推翻布局。
- **将变体连接到真实的修改操作。** 只读原型没问题。如果变体需要修改数据，就将它接到桩实现上：问题是“它应该是什么样子”，而不是“后端是否正常工作”。
- **将原型直接投入生产。** 变体代码是在原型约束下编写的（没有测试，错误处理极少）。融入实际代码时，要按正式要求重新编写。
