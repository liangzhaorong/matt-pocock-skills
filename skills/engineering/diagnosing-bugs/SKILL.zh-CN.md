# 诊断 bug

一套处理棘手 bug 的纪律。只有明确说明理由后，才能跳过某个阶段。

探索代码库时，阅读 `GLOSSARY.md`（如果存在），以便对相关模块建立清晰的心智模型，并查阅你将要修改的领域中的 ADR。

## 脱敏

本技能要求你展示命令、输出和捕获的资料。**先对所有秘密信息脱敏**：用 `<REDACTED>` 替换。构建循环时通过环境变量引用凭据，让凭据留在环境中，而不是出现在展示的内容里。捕获的资料中会带有认证头：只引用能提供诊断线索的行。

如果脱敏后的输出不足以诊断 bug，明确说明并询问用户。

## 阶段 1：建立反馈循环

**这就是本技能的核心。** 其余一切都是机械性的操作。如果你为这个 bug 建立了一个**紧凑**的通过/失败信号（能在遇到*这个* bug 时变红），你就能找到原因；二分定位、假设检验和诊断埋点都只是利用这个信号。如果没有这样的信号，盯着代码看再久也无济于事。

在这里投入远超其他环节的精力。**积极尝试。发挥创造力。拒绝放弃。**

### 构建方式，大致按以下顺序尝试

1. 在能够触及 bug 的接缝处编写**失败测试**：单元测试、集成测试或端到端测试。
2. 针对正在运行的开发服务器执行 **Curl / HTTP 脚本**。
3. 使用固定测试输入**调用 CLI**，将标准输出与已知正确的快照进行差异比较。
4. 使用**无头浏览器脚本**（Playwright / Puppeteer）操作 UI，并对 DOM、控制台或网络进行断言。
5. **重放捕获的跟踪记录。** 将真实的网络请求、载荷或事件日志保存到磁盘；在隔离环境中通过相应代码路径重放。
6. **一次性测试工具。** 启动系统的最小子集（一个服务，依赖使用 mock），通过一次函数调用触发存在 bug 的代码路径。
7. **属性测试 / 模糊测试循环。** 如果 bug 是“有时输出错误”，就运行 1000 个随机输入，寻找失败模式。
8. **二分定位工具。** 如果 bug 出现在两个已知状态（提交、数据集、版本）之间，将“在状态 X 启动、检查、重复”自动化，以便用 `git bisect run` 执行。
9. **差分循环。** 将同一输入分别交给旧版本和新版本（或两种配置）运行，并比较输出差异。
10. **人工参与（HITL）的 bash 脚本。** 最后的手段。如果必须由人点击操作，就用 `scripts/hitl-loop.template.sh` 引导*他们*，使循环仍然保持结构化。捕获的输出会反馈给你。

建立正确的反馈循环，bug 就已经修好了 90%。

### 收紧循环

把循环当作产品来打磨。一旦有了*一个*循环，就**收紧**它：

- 能否让它更快？（缓存准备工作、跳过无关初始化、缩小测试范围。）
- 能否让信号更明确？（对具体症状进行断言，而不是只检查“没有崩溃”。）
- 能否让它更确定？（固定时间、为随机数生成器设置种子、隔离文件系统、冻结网络行为。）

一个耗时 30 秒且结果不稳定的循环，几乎不比没有循环好多少；一个耗时 2 秒、结果确定的循环才称得上紧凑，是调试的强大助力。

### 非确定性 bug

目标不是稳定复现，而是**提高复现率**。将触发操作循环执行 100 次、并行执行、增加压力、缩小时序窗口、插入休眠。发生概率为 50% 的偶发 bug 可以调试；1% 的则不行，所以要不断提高复现率，直到能够调试。

### 确实无法建立循环时

停下来，明确说明情况。列出你尝试过的办法。向用户请求以下其中一项：(a) 能够复现问题的环境的访问权限，(b) 脱敏后的捕获资料（HAR 文件、日志转储、核心转储、带时间戳的屏幕录像），或 (c) 添加临时生产环境诊断埋点的许可。**不要**在没有循环的情况下继续提出假设。

### 完成标准：一个能变红的紧凑循环

阶段 1 完成的条件是：循环既**紧凑**，又**具备变红能力**。你能指出**一条命令**（脚本路径、测试调用或 curl 命令），你**已经至少运行过一次**（展示调用及其输出，并脱敏），且该命令满足：

- [ ] **具备变红能力**：它会触发实际存在 bug 的代码路径，并对**用户描述的确切症状**进行断言，因此能在该 bug 出现时变红、修复后变绿。不能只是“运行时不报错”；它必须能够*捕获这个特定的 bug*。
- [ ] **确定性**：每次运行的判定一致（对于偶发 bug：如上所述，复现率应稳定且足够高）。
- [ ] **快速**：以秒计，而不是以分钟计。
- [ ] **智能体可运行**：你可以无人值守地运行；只有通过 `scripts/hitl-loop.template.sh` 才能让人参与循环。

如果你发现自己在这条命令尚不存在时，就开始阅读代码、构建理论，**停下来：直接跳到假设，正是本技能要防止的失败模式。** 没有具备变红能力的命令，就不能进入阶段 2。

## 阶段 2：复现并最小化

运行循环。观察 bug 出现时循环变红。

确认：

- [ ] 循环产生的是**用户**描述的失败模式，而不是恰好出现在附近的另一种失败。找错 bug，就会修错问题。
- [ ] 多次运行均能复现失败（对于非确定性 bug，复现率应高到足以据此调试）。
- [ ] 已捕获确切症状（错误消息、错误输出、耗时过长），以便后续阶段验证修复确实解决了问题。

### 最小化

循环变红后，将复现用例缩减为**仍然会变红的最小场景**。**每次只削减一项**输入、调用方、配置、数据或步骤，每次削减后重新运行循环，只保留导致失败所必需的部分。

为什么要这样做：最小复现会缩小阶段 3 的假设空间（需要怀疑的可变因素更少），并在阶段 5 成为简洁的回归测试。

当**每个剩余要素都不可或缺**时，才算完成：移除其中任何一个，循环都会变绿。

完成复现**并且**最小化之后，才能继续。

## 阶段 3：提出假设

在检验任何假设之前，先提出 **3–5 个按可能性排序的假设**。只提出一个假设，会让思路锚定在第一个看似合理的想法上。

每个假设都必须**可证伪**：说明它会作出什么预测。

> 格式：“如果 <X> 是原因，那么 <改变 Y> 就会让 bug 消失 / <改变 Z> 就会让它更严重。”

如果你说不出预测，那个假设就只是凭感觉：将其舍弃，或进一步明确。

**检验前，先向用户展示排序后的列表。** 用户通常掌握领域知识，能立即调整排序（“我们刚刚部署了与第 3 项有关的变更”），或者知道哪些假设已经被排除。这是成本很低的检查点，却能节省大量时间。不必等待用户回应；如果用户暂时不在，就按你的排序继续。

## 阶段 4：添加诊断埋点

每个探针都必须对应阶段 3 中的一项具体预测。**每次只改变一个变量。**

工具优先级：

1. 如果环境支持，使用**调试器 / REPL 检查**。一个断点胜过十条日志。
2. 在能够区分不同假设的边界处添加**有针对性的日志**。
3. 绝不要“把所有内容都记入日志，再用 grep 搜索”。

**为每条调试日志加上唯一前缀**，例如 `[DEBUG-a4f2]`。这样，最后清理时只需一次 grep。没有标记的日志容易残留；有标记的日志才能清理干净。

**性能问题分支。** 对于性能回退，日志通常不是合适的手段。应先建立基准测量（计时工具、`performance.now()`、性能分析器、查询计划），再进行二分定位。先测量，再修复。

## 阶段 5：修复与回归测试

在**修复之前**编写回归测试，但前提是存在**合适的接缝**。

合适的接缝，是指测试能够在该处触发调用点上实际发生的**真实 bug 模式**。如果唯一可用的接缝太浅（例如 bug 需要多个调用方才能触发，却只测试单个调用方；单元测试无法复现触发 bug 的调用链），在那里编写回归测试只会带来虚假的信心。

**如果不存在合适的接缝，这本身就是一项发现。** 记录下来。代码库的架构使得这个 bug 无法被测试牢牢约束。将这一点标记出来，留待下一阶段处理。

如果存在合适的接缝：

1. 将最小复现用例转化为该接缝处的失败测试。
2. 观察它失败。如果你通过修改代码或测试夹具强制让测试变红，在信任结果之前，先与未修改的副本做 `diff`，证明修改确实已生效。
3. 应用修复。
4. 观察测试通过。
5. 针对原始（未最小化的）场景，重新运行阶段 1 的反馈循环。

## 阶段 6：清理

在宣布完成之前，必须满足：

- [ ] 原始复现用例已无法再复现问题（重新运行阶段 1 的循环）
- [ ] 回归测试通过（或已记录缺少合适接缝的情况）
- [ ] 已移除所有 `[DEBUG-...]` 诊断埋点（用 `grep` 搜索该前缀）
- [ ] 已删除一次性原型（或将其移至明确标记的调试位置）
- [ ] 已在提交说明 / PR 描述中说明最终被证实的假设，让下一位调试者能从中学习
