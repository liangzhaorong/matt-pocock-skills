# 改进代码库架构

找出架构中的阻力，并提出**深化机会**：通过重构，将浅模块变为深模块。目标是提升可测试性，以及 AI 理解和浏览代码库的便利性。

本命令以项目的领域模型为*参考*，并建立在共享的设计词汇之上：

- 调用 Skill 工具使用 "codebase-design"，获取架构词汇（**模块**、**接口**、**深度**、**接缝**、**适配器**、**杠杆**、**局部性**）及其原则（删除检验、“接口就是测试面”、“一个适配器 = 假想接缝，两个 = 真实接缝”）。在每条建议中准确使用这些术语，不要改用“组件”“服务”“API”或“边界”。
- `GLOSSARY.md` 中的领域语言为好的接缝提供名称；`docs/adr/` 中的 ADR 记录了本命令不应重新争论的决策。

## 流程

### 1. 探索

**先定范围，再扫描：YAGNI（不要做当前不需要的事）。** 深化模块的回报在于让未来对它的修改更容易，因此应更重视代码库中近期发生变更的部分。在开始查看之前，先决定*去哪里*查看：

- 如果用户指定了方向（某个模块、子系统或痛点），就按该方向探索，跳过下面的推断。
- 否则，向前回溯一段足够长的提交历史（`git log --oneline`），找出代码库的热点，也就是反复出现的文件和区域，优先关注这些路径。如果变更分散，没有明显热点，就扩大搜索范围。

先阅读项目的领域术语表（`GLOSSARY.md`），以及你将要涉及的领域中的 ADR。

然后启动一个使用全新上下文窗口的子智能体，遍历代码库。不要遵循僵化的启发式规则；顺着代码自然探索，记录你感到费力的地方：

- 理解一个概念时，哪些地方需要在许多小模块之间来回跳转？
- 哪些模块是**浅模块**，接口几乎与实现一样复杂？
- 哪些地方仅为可测试性而提取了纯函数，但真正的 bug 却藏在调用方式中（缺乏**局部性**）？
- 哪些紧密耦合的模块跨越接缝泄漏了内部细节？
- 代码库的哪些部分未经测试，或者很难通过现有接口测试？

对任何疑似浅模块的对象应用**删除检验**：删除它会让复杂度集中起来，还是只会转移复杂度？“会让复杂度集中起来”就是你要寻找的信号。

### 2. 以 HTML 报告呈现候选项

将一个自包含的 HTML 文件写入操作系统的临时目录，避免在仓库中留下文件。优先从 `$TMPDIR` 获取临时目录，未设置时使用 `/tmp`（Windows 上使用 `%TEMP%`），并写入 `<tmpdir>/architecture-review-<timestamp>.html`，使每次运行都生成一个新文件。为用户打开该文件（Linux 上使用 `xdg-open <path>`，macOS 上使用 `open <path>`，Windows 上使用 `start <path>`），并告知其绝对路径。

报告通过 **CDN 加载 Tailwind** 来处理布局和样式；当图、流程图或时序图能可靠地表达结构时，通过 **CDN 加载 Mermaid** 来绘图。将 Mermaid 与手工制作的 CSS/SVG 视觉元素结合：关系呈图结构时（调用图、依赖关系、时序）使用 Mermaid；想要更具编辑设计感的表现时（体量示意图、剖面图、折叠动画），使用手工构建的 div/SVG。每个候选项都要有**改造前后的可视化对比**。充分使用视觉表达。

为每个候选项渲染一张卡片，包含：

- **文件**：涉及哪些文件或模块
- **问题**：当前架构为何造成阻力
- **解决方案**：用通俗英语说明会发生哪些变化
- **收益**：从局部性和杠杆的角度解释，并说明测试会如何改善
- **改造前 / 改造后示意图**：并排展示、定制绘制，说明当前的浅层结构及深化后的效果
- **推荐程度**：使用 `Strong`、`Worth exploring`、`Speculative` 之一，以徽章呈现

在报告末尾加入**首选建议**部分：你会先处理哪个候选项，以及原因。

**领域概念使用 GLOSSARY.md 中的术语，架构概念使用 `/codebase-design` 中的术语。** 如果 `GLOSSARY.md` 定义了“Order”，就说“Order 接收模块”，不要说“FooBarHandler”，也不要说“Order 服务”。

**ADR 冲突**：如果某个候选项与现有 ADR 相矛盾，只有当前架构确实造成了足够大的阻力、值得重新审视该 ADR 时，才提出它。在卡片中明确标记（例如使用警告提示框：*“与 ADR-0007 相矛盾，但值得重新讨论，因为……”*）。不要把 ADR 禁止的所有理论上可行的重构都列出来。

完整的 HTML 骨架、图表模式和样式指导，参见 [HTML-REPORT.md](HTML-REPORT.md)。

此时不要提出接口方案。文件写完后，询问用户：“你想深入探索其中哪一个？”

### 3. 深入追问循环

用户选定候选项后，调用 Skill 工具使用 "grilling"，与用户一起逐步梳理决策树：约束、依赖、深化后模块的形态、接缝背后包含什么，以及哪些测试应当保留。

随着决策逐渐明确，相关的伴随更新应即时进行；调用 Skill 工具使用 "domain-modeling"，在推进过程中持续更新领域模型：

- **用 `GLOSSARY.md` 中不存在的概念为深化后的模块命名？** 将该术语加入 `GLOSSARY.md`。如果文件不存在，按需创建。
- **在对话中澄清了模糊术语？** 立即更新 `GLOSSARY.md`。
- **用户基于关键理由否决了候选项？** 提议记录 ADR，表述为：*“要我把这一点记录为 ADR，避免今后的架构审查再次提出同样建议吗？”* 只有未来的探索者确实需要知道该理由，才能避免再次提出同样建议时，才这样提议；跳过暂时性的理由（“现在不值得做”）以及不言自明的理由。
- **想为深化后的模块探索不同的接口方案？** 调用 Skill 工具使用 "codebase-design"，并采用其中的 design-it-twice 并行子智能体模式。
