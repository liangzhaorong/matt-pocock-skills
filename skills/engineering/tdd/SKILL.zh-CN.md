# 测试驱动开发

TDD 就是红 → 绿的循环。本技能是一份参考，用来让这个循环产出值得保留的测试：什么是好测试、测试应放在哪里、反模式，以及循环的规则。每一节都适用于每一次循环：在循环开始前和进行中查阅它们，而不是事后才看。

在探索代码库时，先阅读 `GLOSSARY.md`（如果存在），以便测试名称和接口词汇与项目的领域语言保持一致，并遵守你所改动区域内的 ADR（架构决策记录）。

## 什么是好测试

测试通过公共接口验证行为，而不是实现细节。代码可以彻底改变；测试则不应该。一个好测试读起来像一份规格说明："用户可以用有效的购物车结账" 准确地告诉你存在什么能力，而且它能挺过重构，因为它不关心内部结构。

示例见 [tests.md](tests.md)，mock（模拟）指南见 [mocking.md](mocking.md)。

## 接缝：测试放在哪里

**接缝（seam）** 是你进行测试的公共边界：在不深入内部的前提下观察行为的接口。测试位于接缝上，绝不针对内部实现。

**只在事先商定的接缝上测试。** 在编写任何测试之前，先写下待测的接缝并与用户确认。不在未确认的接缝上编写任何测试。你无法测试所有东西，因此事先商定接缝，正是让测试精力落在关键路径和复杂逻辑上、而不是摊到每个边缘情况上的方法。

问一句："公共接口是什么？我们应该测试哪些接缝？" 给每个提议的接缝写一行备注，说明它能捕获什么、又会遗漏什么。

当该接口本身的形态尚有疑问时（模块应该多深、接缝应放在哪里、接口应暴露什么），用 Skill 工具调用 "codebase-design" 来获取这套词汇。它是 module、interface、depth、seam、adapter、leverage、locality 这些术语的共同出处；它是一份供查阅的参考，而不是一个要运行的会话。

## 反模式

- **与实现耦合**：mock 内部协作者、测试私有方法，或通过旁路验证（直接查询数据库而不是使用接口）。识别信号：行为并没有变，重构却让测试挂了。
- **同义反复**：断言用与代码相同的方式重新计算期望值（`expect(add(a, b)).toBe(a + b)`、用同样方式手工推导出的快照、断言某个常量等于它自身），因此它从构造上就必然通过，永远不可能与代码不一致。期望值必须来自独立的真相来源：一个已知正确的字面值、一个人工推演的示例、或规格说明。
- **水平切片**：先写完所有测试，再写所有实现。批量测试验证的是 *想象出来的* 行为：你测试的是事物的 *形状* 而不是面向用户的行为，测试对真实变化变得不敏感，而且你在理解实现之前就锁定了测试结构。应改用 **垂直切片** 工作：一个测试 → 一段实现 → 重复，每个测试都是一颗 **曳光弹**（tracer bullet），对上一个循环教给你的东西做出回应。

## 循环的规则

- **先红后绿。** 先写失败的测试，然后只写刚好让它通过的代码。不要预判未来的测试，也不要添加投机性的功能。
- **一次一个切片。** 每个循环一个接缝、一个测试、一个最小实现。
- **重构不属于这个循环。** 它属于评审阶段（见 `code-review` 技能），而不属于红 → 绿的实现循环。
