# Ask Matt

你不可能记住每一个技能，所以来问 Matt。

在断言某个技能做什么、或建议跳过某个步骤之前，先读那个技能的 SKILL.md：这里的摘要只用于定向。

**流程**（flow）是一条穿行于各技能之间的路径。大多数路径都沿着一条**主流程**（main flow）运行，另有两条**入口匝道**（on-ramps）汇入其中。其余的一切要么完全独立，要么是运行在底层的一层词汇。

## 主流程：想法 → 交付

大多数工作走的都是这条路线：你有一个想法，想把它做出来。

1. **`/grill-with-docs`** 通过访谈打磨想法。只要你**是在某个工作目录中工作**，就从这里开始：它是有状态的，会把学到的东西留存在 `GLOSSARY.md` 和 ADR 里。（没有工作目录？改用 `/grill-me`，见“独立技能”一节。两者运行的是同一个 `/grilling` 原语；`grill-with-docs` 会留下书面记录，所以只要存在一个可以留记录的仓库，它就是两者中更好的那个。）
2. **分支：每个问题都能在对话中敲定吗？** 如果某个问题需要的是一个可运行的答案（状态、业务逻辑、一个你必须亲眼看到的 UI），就绕道原型，去程和回程都由 **`/handoff`** 桥接（原型住在其专属目录里，而这正是 `/handoff` 的用途；见“阶段边界”）：
   - 用 **`/handoff`** 交出上下文，然后针对那个文件开一个全新会话；
   - 用 **`/prototype`** 以一次性代码回答那个问题；
   - 用 **`/handoff`** 把你学到的东西传回来，并在最初那条想法对话线程中引用它。
3. **分支：这是一次跨会话的构建吗？**
   - **是** → **`/to-spec`**（把整段对话线程变成规格），再用 **`/to-tickets`** 拆成曳光弹式工单（tracer-bullet tickets），每张工单都声明自己的**阻塞边**（blocking edges）。然后用以下两种方式之一来消化这些工单：
     - 逐张工单跑 **`/implement`**，**每张之间 `/clear` 清空上下文**。在本地追踪器上，就是 `.scratch/<feature>/issues/` 下每张工单一个文件，按阻塞优先的顺序手工推进；在真正的追踪器上，这些边会变成原生的阻塞链接，于是任何阻塞项都已完成 的工单都可以直接认领。每张工单都自包含，所以连最后一张的上下文也是用完即弃的。
     - 用 **`/implement-spec`** 一口气跑完整份规格。它把这些工单当作一张**任务图**（task graph）来读，在就绪的**前沿**（frontier）上并行运行实现者子代理，并把所有成果落到一条**集成分支**（integration branch）上。当你宁愿编排整个构建、而不是亲自驱动每张工单时，就用它。
   - **否** → 就在此地、在同一个上下文窗口里 **`/implement`**。

   无论哪条路，代码都是靠驱动 **`/tdd`**（一次一个红绿切片）建起来的，并以 **`/code-review`** 收尾：一份对 diff 的双轴评审（标准 + 规格）。`/implement` 对每张工单都跑这两样；`/implement-spec` 的各个实现者分别驱动 `/tdd`，它自己则在集成分支上跑一次 `/code-review`。当你只想以测试先行的方式构建一个具体行为、而不需要完整规格时，可单独使用 **`/tdd`**；当你想相对某个固定基准点评审一个分支或 PR 时，随时可单独使用 **`/code-review`**。

   当工作以 pull request 的形式提交时，**`/pr`** 负责塑形正文：展示这次变更的最小视觉呈现、证明它可用的前后对比证据，以及一次单向门还是双向门的判断。它是模型调用的，所以代理每逢写 PR 都会用它。

4. **`/retro`** 闭合循环。一次构建之后，尤其是跑偏的那次，它会回看整个会话，并建议改动代理的**环境**，而不是代码：导航指针、自动化检查、`/code-review` 所执行的编码标准、引导文件（steering files）、工具链。机械性的失误变成确定性检查；判断性的取舍变成编码标准。下一次构建便从一个更好的环境起步。

### 上下文管理

把第 1 到 3 步保持在**同一个不间断的上下文窗口**里（直到 `/to-tickets` 之后再 compact 或 clear），让拷问、规格和工单都建立在同一套思考之上。随后的每个 `/implement` 都全新起步，依据工单本身工作。`/retro` 要在它所回看的那个会话里运行，且要在你 clear 之前；clear 之后，就改为把它指向那个会话的日志。

这样做的上限是 **[smart zone](https://www.aihero.dev/ai-coding-dictionary/smart-zone)**：模型仍能敏锐推理的那个窗口（在最先进的模型上约为 150k token）。如果某个会话在 `/to-tickets` 之前就逼近了这个上限，不要在降级状态下硬撑；在最近的阶段边界处 `/compact`，然后继续（见“阶段边界”）。

## 入口匝道

一类先产生工作、随后汇入主流程的起始处境。

- **Bug 和请求越堆越多** → **`/triage`**。它让 issue 依次经过各个分诊角色，产出代理可直接开工的 issue，之后再由 **`/implement`** 接手。

  分诊只针对**不是你创建的** issue：bug 报告、外部来的功能请求、任何以原始状态抵达的东西。`/to-tickets` 产出的工单已经对代理就绪，所以**不要对它们分诊**。

- **有东西坏了** → **`/diagnosing-bugs`**。为难缠的那些准备：第一眼看不穿的 bug、间歇性失败（flake）、在两个已知良好状态之间悄悄潜入的回归。在拥有**紧凑反馈回路**（tight feedback loop，一条已经能在*这个* bug 上变红的命令）之前，它拒绝提出理论；之后用回归测试完成修复。修复落地后，在同一会话里运行 **`/retro`**，追问什么本可以阻止这个 bug；如果真正的发现是没有一条好接缝（seam）能把它锁住，那就是 **`/improve-codebase-architecture`** 的活儿。

- **庞大而朦胧的工作量：绿地项目或超大功能构建，大到一次会话装不下** → **`/wayfinder`**，这里是认知负担最重的流程。当从这里到目的地的路径尚不可见时，它会在 issue 追踪器上绘制一张由**决策工单**（decision tickets）构成的**共享地图**，并逐一解决，产出**决策而非交付物**，直到迷雾被步步逼退、路径清晰。**`/grill-with-docs`** 打磨的是一个会话装得下的想法；wayfinder 面对的是装不下的那种，而且它更慢、更稠密，所以只为此保留，绝不用于范围已经清晰的功能。

  当地图变清晰后，**它交棒，不施工**：在 **`/to-spec`** 处汇入主流程，由它把地图上相互链接的决策收拢成一份可构建的计划，然后照常 `/to-tickets` 和 `/implement`。把地图直接循环进 `/implement` 会跳过这次收拢、丢掉相互链接的细节，所以只有当工作量证明确实很小时，才直接进 `/implement`。

## 代码库健康

不是功能开发，只是养护。

- **`/improve-codebase-architecture`** 有空就可以跑，让代码库持续处于适合代理作业的状态。它呈现**深化机会**（deepening opportunities）；选中一个就_生成了一个想法_，可以带进主流程的 `/grill-with-docs`。它是找到候选者的勘察；**`/codebase-design`**（见下文）是你对选中者做设计的工作台。

## 底层词汇

两个由模型调用的参考资料，*运行在其他技能之下*，各自是其词汇的唯一权威来源。当问题出在**措辞**而非流程上时，可直接使用它们；否则就让上面的技能自行引入。

- **`/domain-modeling`**：磨利项目的*领域*语言：质疑一个含糊的术语，化解一个被重载的词（身兼三职的 "account"），把一个难以逆转的决策记录成 ADR。它是 `/grill-with-docs` 所驱动的主动纪律，让 `GLOSSARY.md` 保持为一部干净的词汇表。
- **`/codebase-design`** 是深模块词汇表（模块、接口、深度、接缝、适配器、杠杆、局部性），用于设计模块的*形态*：大量行为藏在一个干净接缝上的小接口背后。`/tdd` 和 `/improve-codebase-architecture` 说的都是这门语言。

## 阶段边界

**阶段**（phase）是会话内的一块工作：拷问、实现、QA。在两个阶段之间的**边界**上，你有五个选项，而在它们之间做选择是整张地图中最模糊的决策：

- **继续**（Continue）：原地不动。不花成本，也不丢东西。
- **`/clear`**：清空窗口，当这里的内容对接下来毫无影响时用。
- **`/handoff`** 写出一份可携带的 markdown 文件。适用面很窄：仅用于**新的 harness**（运行环境）、**新目录**、**同事**，或在**阶段中途**分出一条支线任务。它换来的是可携带性。
- **子代理**（Subagent）：把一个范围收得很紧的任务送进它自己的窗口，收回一份报告。
- **`/compact`** 压缩当前上下文，并用它播种一个新会话。**默认项**，位于决策树的最底层，而不是第一个伸手的选择。

阅读 [PHASE-BOUNDARIES.md](PHASE-BOUNDARIES.md) 了解那棵有序的决策树：五个问题、每个分支背后的理由，以及为什么一手来源（primary source）的代价使**继续**成为第一个要排除的选项。在边界**上**做这个决策；阶段中途则要么继续，要么把剩余工作拆给子代理。

## 独立技能

完全不在主流程上。

- **`/grill-me`**：与 `/grill-with-docs` 同样穷追不舍的访谈，但**无状态**：不在本地保存任何东西，也不构建 `GLOSSARY.md`。当你**不在工作目录中工作**时用它（打磨一份计划、一个设计、一篇文章，任何底下没有仓库的东西）。如果你就在工作目录里，改用 `/grill-with-docs`：它跑的是同样的访谈，还会留下书面记录，所以严格来说更好。
- **`/grilling`** 是访谈原语本身：轮次、前沿、查事实是代理的活、做决策是你的活。`/grill-me` 和 `/grill-with-docs` 是两个具名入口，而 `/triage`、`/wayfinder` 和 `/improve-codebase-architecture` 都在内部运行它。只有当你想要一场不带任何包装的访谈时，才直接使用它。
- **`/prototype`** 是一个回答单一设计问题的小型一次性程序：这个状态模型感觉对不对，或者这个 UI 应该长什么样。“一次性”是对代码写法的约束，不是将其销毁的承诺：答案会折进真正的代码里，而原型本身会作为**一手来源**（primary source）保存在一条从 main 切出的 `prototype/<name>` 分支上，由实现 issue 指向它。它是主流程第 2 步中的那条绕道，但任何时候，只要一个设计问题在纸面上难以敲定，都可以用它。
- **`/research`**：把阅读跑腿的活儿委托给**后台代理**：它对照**一手来源**调查一个问题，然后在仓库里留下一份带引用的 Markdown 文件。它读的时候，你继续干活。它产出的文件是要*带进*主流程 `/grill-with-docs` 的东西，因为研究是在给思考喂料，而不是取代思考。
- **`/to-questionnaire`** 登场的时机：卡住你的东西既不在你脑子里，也不在代码库里，而在**别人的**脑子里；它会替你写出一份让对方填写的问卷。它是 `/grill-me` 的反向：不是就主题访谈你，而是就**这次发送**访谈你（发给谁、需要收回什么），并把问题对准那道缺口。收回来的东西是 `/grill-with-docs` 或 `/to-spec` 的原料。
- **`/wizard`** 用于只有**人类**才能执行的步骤：开通基础设施、配置凭据或 CI 密钥、在一个陌生的第三方控制台里一路点过去、执行一次性的迁移或切换。它生成一个交互式 bash 脚本，依次打开每个 URL、捕获每个值，并写入 `.env` 和 GitHub secrets，让这套流程不再是你每次都要向代理重新解释一遍的东西。它是模型调用的，所以代理一碰到只有你能通过的墙，就会用它。如果代理自己就能做，那就该它自己做；这个技能是留给真正需要人参与的环节的。
- **`/wait-what`** 是对一条没接住的消息的纠偏。在对话中途、在任何其他技能内部都可以用：代理会补上你原本缺失的上下文，用大白话、使用 `GLOSSARY.md` 的词汇，把它刚说过的话重新讲一遍。它是事后补救；`/grill-with-docs` 是事前预防，因为早早约定的共同语言，才能让行话根本不出场。
- **`/teach`**：跨多个会话学习一个概念，把当前目录用作有状态的工作区。
- **`/writing-for-agents`** 是撰写代理所读文档的参考：技能、AGENTS.md、被指针指向的文档。

## 前置条件

**`/setup-matt-pocock-skills`**：在你第一次跑工程流程之前运行，配置其他技能默认依赖的 issue 追踪器、分诊标签和文档布局。自定义 issue 追踪器同样适用。
