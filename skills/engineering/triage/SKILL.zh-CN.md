# 分诊（Triage）

把项目 issue 跟踪器上的 issue 放进一个由分诊角色构成的小型状态机中流转。

如果本仓库把外部 PR 也当作一种请求入口（见 issue 跟踪器配置），那么分诊同样覆盖它们：**PR 就是附带了代码的 issue**，使用相同的角色、相同的状态和同一台状态机，下文少数差异之处会标注"针对 PR"。裸写的 `#42` 按跟踪器配置解析为 issue 或 PR。

分诊期间发布到 issue 跟踪器的每条评论或 issue **必须**以下面这段免责声明开头：

```
> *本内容由 AI 在分诊期间生成。*
```

## 参考文档

- [AGENT-BRIEF.md](AGENT-BRIEF.md)：如何撰写经久耐用的代理简报
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)：`.out-of-scope/` 知识库如何运作

## 角色

两个**分类**角色：

- `bug`：有东西坏了
- `enhancement`：新功能或改进

五个**状态**角色：

- `needs-triage`：需要维护者评估
- `needs-info`：等待报告者补充信息
- `ready-for-agent`：规格已完整，可交给无人值守（AFK）的代理
- `ready-for-human`：需要人来实现
- `wontfix`：不会处理

对于 PR，同样的状态要对照附带的代码来解读：`ready-for-agent` 表示简报已附上、代理应在该 diff 上推进下一步；`ready-for-human` 表示已准备好由人来合并。

每个经过分诊的 issue 应当恰好带一个分类角色和一个状态角色。如果状态角色互相冲突，先标记出来并询问维护者，再做其他任何事。

这些是规范角色名（canonical role names）。issue 跟踪器里实际使用的标签字符串可能不同。映射关系本应已提供给你；如果没有，请让用户运行 `/setup-matt-pocock-skills`。

状态流转：未打标签的 issue 通常先进入 `needs-triage`；再从那里流转到 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。报告者回复后，`needs-info` 回到 `needs-triage`。维护者随时可以推翻；流转若有异常迹象，先标记并询问再继续。

## 调用

维护者调用 `/triage`，用自然语言描述想要什么。理解请求并行动。示例：

- "给我看看所有需要我关注的东西"
- "我们来看看 #42"（issue 或 PR）
- "把 #42 移到 ready-for-agent"
- "有哪些是代理可以认领的？"

## 展示需要关注的内容

查询 issue 跟踪器，展示三个桶，最旧的在前：

1. **未打标签**：从未分诊过。
2. **`needs-triage`**：评估进行中。
3. **`needs-info` 且报告者在上次分诊备注之后有新动态**：需要重新评估。

当 PR 在范围内时，把外部 PR 也纳入这些桶，并给每行加上 `[PR]` 或 `[issue]` 标记。发现环节只呈现*外部* PR（谁算外部由跟踪器配置定义），因此协作者进行中的 PR 不属于分诊工作。该过滤只用于发现环节；被明确点名的 PR 无论作者是谁都会被分诊。

显示各桶数量，并给每个条目一行摘要。让维护者来挑。

## 分诊某个具体的 issue 或 PR

1. **收集上下文。** 通读整个 issue 或 PR（正文、评论、标签、作者、日期；PR 还要读 diff）。解析此前的分诊备注，避免重复询问已解决的问题。使用项目的领域词汇表探索代码库，并遵守相关区域内的 ADR。对代码库跑两项检查：(a) **冗余**：按领域概念（而不只是请求的字面措辞）搜索所请求的行为是否已有实现，并报告你查过哪里。如果找到了，这就是一个"已实现"情形的 `wontfix`（见第 5 步）。(b) **此前被拒绝过**：阅读 `.out-of-scope/*.md`，把与该请求相似的条目呈现出来。

2. **给出建议。** 告诉维护者你的分类与状态建议及理由，附上一段与该请求相关的代码库简述（包括是否已实现）。等待指示。

3. **验证主张。** 在任何拷问之前，先确认主张站得住脚。对于 bug，按报告者的步骤复现。对于 PR，确认 diff 确实做到了它声称的事：检出它，运行相关的测试或命令。报告结果：已确认（附代码路径）、失败，或细节不足（强烈的 `needs-info` 信号）。一次成功的验证会让代理简报有力得多。

4. **拷问（如有需要）。** 如果请求需要充实，调用两次 Skill 工具，分别传入 "grilling" 和 "domain-modeling"，一轮一轮地用问题把它拷问成形，同时随着决策落定，就地打磨领域术语并更新 `GLOSSARY.md`/ADR。

5. **落实结果：**
   - `ready-for-agent`：发布代理简报评论（见 [AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human`：与代理简报结构相同，但要注明为什么不能委派（判断性决策、外部访问权限、设计决策、手工测试）。
   - `needs-info`：发布分诊备注（模板见下）。
   - `wontfix`：关闭 issue，评论内容取决于*为什么*：
     - **已实现**：该改动已存在于代码库中。指出它在哪里；**不要**写入 `.out-of-scope/`（那个知识库是给*被拒绝*的请求用的，不是给已建成的功能用的）。
     - **被拒绝（bug）**：礼貌地解释，然后关闭。
     - **被拒绝（enhancement）**：写入 `.out-of-scope/`，在评论中链接它，然后关闭（见 [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage`：应用该角色。如有部分进展，可酌情评论。

## 快速状态覆盖

如果维护者说"把 #42 移到 ready-for-agent"，相信他们，直接应用该角色。先确认你将要做的事（角色变更、评论、关闭），然后行动。跳过拷问。如果在没有经过拷问的情况下移到 `ready-for-agent`，询问他们是否想写一份代理简报。

## Needs-info 模板

```markdown
## 分诊备注（Triage Notes）

**目前已确认的事实：**

- 要点 1
- 要点 2

**仍需你补充的信息（@reporter）：**

- 问题 1
- 问题 2
```

把拷问期间已解决的所有内容记入"目前已确认的事实"，这些工作才不会丢失。问题必须具体、可行动，不能是"请提供更多信息"。

## 恢复上一次会话

如果 issue 或 PR 上存在此前的分诊备注，先阅读它们，检查报告者是否已回答任何悬而未决的问题，并在继续之前呈现更新后的全貌。不要重复询问已解决的问题。
