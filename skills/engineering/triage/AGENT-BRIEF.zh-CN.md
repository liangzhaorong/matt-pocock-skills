# 撰写代理简报（Agent Brief）

代理简报是当 issue 或 PR 流转到 `ready-for-agent` 时发布在其上的一条结构化评论。它是无人值守（AFK）代理开展工作的权威规格。原始正文和讨论只是上下文：代理简报才是契约。

简报说明**代理应该做什么**，这在两种场景下各有延伸：对 issue 而言，是从零开始构建改动；对 PR 而言，是*在现有 diff 上*还剩什么要做：完成它、补齐缺口、处理评审意见。两种场景原则相同；下面的 PR 示例展示了差异。

## 原则

### 耐用性优先于精确性

issue 可能在 `ready-for-agent` 状态停留数天或数周，期间代码库会发生变化。写简报时要让它即使随着文件被重命名、移动或重构，仍然保持有用。

- **要** 描述接口、类型和行为契约
- **要** 点出代理需要查找或修改的具体类型、函数签名或配置结构
- **不要** 引用文件路径：它们会过期失效
- **不要** 引用行号
- **不要** 假定当前的实现结构会保持不变

### 描述行为，而非过程

描述系统**应该做什么**（WHAT），而不是**如何实现**（HOW）。代理会全新地探索代码库，自行做出实现决策。

- **好：** "`SkillConfig` 类型应接受一个类型为 `CronExpression` 的可选 `schedule` 字段"
- **坏：** "打开 src/types/skill.ts，在第 42 行加一个 schedule 字段"
- **好：** "当用户不带参数运行 `/triage` 时，应看到需要关注的 issue 摘要"
- **坏：** "在主处理函数里加一个 switch 语句"

### 完整的验收标准

代理需要知道什么时候算完成。每份代理简报必须有具体、可测试的验收标准。每条标准都应可独立验证。

- **好：** "运行 `gh issue list --label needs-triage` 会返回已经过初步分类的 issue"
- **坏：** "分诊功能应正常工作"

### 明确的范围边界

写明什么不在范围内。这能防止代理"镀金"（做未要求的过度完善）或对相邻功能自作主张。

## 模板

```markdown
## 代理简报（Agent Brief）

**分类：** bug / enhancement
**摘要：** 一行描述需要完成什么

**当前行为：**
描述现在发生的情况。对 bug，这里写出错的行为；
对 enhancement，这里写该功能所基于的现状。

**期望行为：**
描述代理的工作完成之后应该发生什么。
要写清楚边缘情况和错误条件。

**关键接口：**
- `TypeName`：需要改什么、为什么
- `functionName()` 的返回类型：现在返回什么、应该返回什么
- 配置结构：需要新增的任何配置项

**验收标准：**
- [ ] 具体、可测试的标准 1
- [ ] 具体、可测试的标准 2
- [ ] 具体、可测试的标准 3

**不在范围内：**
- 本 issue 中不应改动或处理的东西
- 看似相关、实则独立的相邻功能
```

## 示例

### 好的代理简报（bug）

```markdown
## 代理简报（Agent Brief）

**分类：** bug
**摘要：** 技能描述截断会在单词中间切断，产生破损输出

**当前行为：**
当技能描述超过 1024 个字符时，会在恰好 1024 个字符处截断，
完全无视单词边界。这会产生在单词中间戛然而止的描述
（例如 "Use when the user wants to confi"）。

**期望行为：**
截断应在 1024 个字符之前的最后一个单词边界处断开，
并追加 "..." 以指示发生了截断。

**关键接口：**
- `SkillMetadata` 类型的 `description` 字段：类型本身无需改动，
  但填充该字段的校验/处理逻辑需要尊重单词边界
- 任何读取 SKILL.md frontmatter 并提取描述的函数

**验收标准：**
- [ ] 1024 字符以内的描述保持不变
- [ ] 超过 1024 字符的描述在 1024 字符前最后一个单词边界处截断
- [ ] 截断后的描述以 "..." 结尾
- [ ] 含 "..." 在内的总长度不超过 1024 个字符

**不在范围内：**
- 修改 1024 字符上限本身
- 多行描述支持
```

### 好的代理简报（enhancement）

```markdown
## 代理简报（Agent Brief）

**分类：** enhancement
**摘要：** 增加对 `.out-of-scope/` 目录的支持，用于跟踪被拒绝的功能请求

**当前行为：**
功能请求被拒绝时，issue 会被加上 `wontfix` 标签关闭并附一条评论。
决策及其理由没有持久的记录。将来出现类似请求时，维护者只能凭记忆
回忆或自行搜索此前的讨论。

**期望行为：**
被拒绝的功能请求应记录在 `.out-of-scope/<concept>.md` 文件中，
包含决策、理由，以及指向所有请求过该功能的 issue 的链接。
分诊新 issue 时，应检查这些文件是否有匹配项。

**关键接口：**
- `.out-of-scope/` 中的 Markdown 文件格式：每个文件应有一个
  `# Concept Name` 标题、一行 `**Decision:**`、一行 `**Reason:**`，
  以及一个带 issue 链接的 `**Prior requests:**` 列表
- 分诊工作流应尽早读取所有 `.out-of-scope/*.md` 文件，
  并按概念相似度将新进的 issue 与之匹配

**验收标准：**
- [ ] 以 wontfix 关闭一个功能时，会在 `.out-of-scope/` 中创建/更新文件
- [ ] 该文件包含决策、理由和指向被关闭 issue 的链接
- [ ] 若匹配的 `.out-of-scope/` 文件已存在，新 issue 会被追加到其
      "Prior requests" 列表，而不是创建重复文件
- [ ] 分诊时会检查现有的 `.out-of-scope/` 文件，当新 issue 与
      此前的拒绝相匹配时将其呈现出来

**不在范围内：**
- 自动匹配（由人来确认匹配）
- 重新打开此前被拒绝的功能
- bug 报告（只有 enhancement 的拒绝才进入 `.out-of-scope/`）
```

### 好的代理简报（PR）

对 PR 而言，"当前行为"描述的是 diff 的现状，简报要求代理去完成或修复它，而不是从零构建。

```markdown
## 代理简报（Agent Brief）

**分类：** enhancement
**摘要：** 完成贡献者为 `triage list` 实现的 `--json` 输出标志

**当前行为：**
该 PR 添加了一个 `--json` 标志，把 issue 列表序列化为 JSON。
主路径可用，diff 也符合项目的命令结构。但还有两个缺口：
错误仍以人类可读文本打印（不是 JSON），且新标志没有测试覆盖。

**期望行为：**
带 `--json` 时，所有输出（包括错误）都是 stdout 上格式良好的 JSON，
命令的退出码保持不变。不带该标志时，现有的人类可读输出原样保留。

**关键接口：**
- 该命令的错误路径在 `--json` 下应输出 `{ "error": string }`，
  而不是纯文本错误
- 复用该 PR 已添加的序列化器；不要引入第二个

**验收标准：**
- [ ] `triage list --json` 在成功和错误两种情况下都输出有效 JSON
- [ ] 退出码与不带 --json 的命令一致
- [ ] 有一个测试覆盖 `--json` 的成功输出和一个错误场景
- [ ] 默认（非 JSON）输出逐字节保持不变

**不在范围内：**
- 给其他任何命令添加 `--json`
- 修改该 PR 已定义的成功负载 JSON 结构
```

### 坏的代理简报

```markdown
## 代理简报（Agent Brief）

**摘要：** 修掉分诊的 bug

**要做什么：**
分诊那玩意儿坏了。看看主文件，把它修了。
问题出在大约 150 行附近的那个函数。

**要改的文件：**
- src/triage/handler.ts（第 150 行）
- src/types.ts（第 42 行）
```

这份简报的问题在于：

- 没有分类
- 描述含糊（"分诊那玩意儿坏了"）
- 引用了终将过期失效的文件路径和行号
- 没有验收标准
- 没有范围边界
- 没有描述当前行为与期望行为
