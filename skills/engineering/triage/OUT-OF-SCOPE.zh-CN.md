# 范围外知识库（Out-of-Scope Knowledge Base）

仓库中的 `.out-of-scope/` 目录存放被拒绝的功能请求的持久记录。它有两个用途：

1. **组织记忆**：记录一个功能为什么被拒绝，这样即使 issue 被关闭，理由也不会丢失
2. **去重**：当新 issue 与此前的某次拒绝相匹配时，技能可以呈现先前的决策，而不是重新争论一遍

## 目录结构

```
.out-of-scope/
├── dark-mode.md
├── plugin-system.md
└── graphql-api.md
```

每个**概念**一个文件，而不是每个 issue 一个。请求同一件事的多个 issue 归入同一个文件。

## 文件格式

文件应以轻松、可读的风格撰写，更像一篇短小的设计文档，而不是一条数据库记录。使用段落、代码示例和例子，让理由清晰易懂，对第一次读到它的人也有用。

```markdown
# Dark Mode

本项目不支持深色模式或面向用户的主题化。

## 为什么这超出了范围

渲染管线假定在 `ThemeConfig` 中定义了单一调色板。支持多主题将需要：

- 一个包裹整个组件树的主题上下文提供者
- 每个组件各自做主题感知的样式解析
- 一个存储用户主题偏好的持久化层

这是一次重大的架构变更，与本项目专注于内容创作的方向不符。
主题化是嵌入或再分发其产物的下游使用者才需要关心的事。

```ts
// 当前的 ThemeConfig 接口并非为运行时切换而设计：
interface ThemeConfig {
  colors: ColorPalette; // 单一调色板，构建时解析
  fonts: FontStack;
}
```

## 先前的请求（Prior requests）

- #42: "Add dark mode support"
- #87: "Night theme for accessibility"
- #134: "Dark theme option"
```

### 文件命名

给概念取一个简短、具描述性的 kebab-case 名字：`dark-mode.md`、`plugin-system.md`、`graphql-api.md`。名字要有足够辨识度，让浏览目录的人不用打开文件就知道被拒绝的是什么。

### 撰写理由

理由必须有实质内容：不是"我们不想要这个"，而是为什么。好的理由会引用：

- 项目范围或理念（"本项目专注于 X；主题化是下游关心的事"）
- 技术约束（"支持它需要 Y，而 Y 与我们的 Z 架构冲突"）
- 战略决策（"我们选择用 A 而不是 B，因为……"）

理由应当经久耐用。避免引用临时状况（"我们现在太忙了"）；那不是真正的拒绝，只是推迟。

## 何时查阅 `.out-of-scope/`

分诊期间（第 1 步：收集上下文），读取 `.out-of-scope/` 下的所有文件。评估新 issue 时：

- 检查该请求是否匹配某个现有的范围外概念
- 匹配依据是概念相似度，不是关键词："night theme" 能匹配 `dark-mode.md`
- 若有匹配，把它呈现给维护者："这与 `.out-of-scope/dark-mode.md` 相似。我们之前拒绝过它，理由是[原因]。你现在还是同样的看法吗？"

维护者可以：

- **确认**：新 issue 被加入现有文件的 "Prior requests" 列表，然后关闭
- **重新考虑**：删除或更新该范围外文件，issue 走正常分诊流程
- **不同意匹配**：两个 issue 相关但不同，走正常分诊流程

## 何时写入 `.out-of-scope/`

只有当 **enhancement**（而不是 bug）被*拒绝*为 `wontfix` 时才写入。这对 enhancement PR 与对 issue 完全同样适用：被拒绝的 PR 也记录在此，同一请求就不会换一副新代码卷土重来。

当某个东西因**已实现**而被关闭为 `wontfix` 时，**不要**写到这里。那是已建成的功能，不是被拒绝的请求；记录它会用虚假的拒绝污染去重检查。正确的做法是，在关闭评论中指出该功能已经存在于何处。

流程：

1. 维护者判定某个功能请求超出范围
2. 检查是否已存在匹配的 `.out-of-scope/` 文件
3. 若存在：把新 issue 追加到 "Prior requests" 列表
4. 若不存在：以概念名新建文件，写上决策、理由和第一条先前的请求
5. 在 issue 上发一条评论，解释决策并提到 `.out-of-scope/` 文件
6. 给 issue 打上 `wontfix` 标签并关闭

## 更新或删除范围外文件

如果维护者对一个此前被拒绝的概念改变了主意：

- 删除该 `.out-of-scope/` 文件
- 技能不需要重新打开旧 issue；它们是历史记录
- 触发这次重新考虑的新 issue 走正常分诊流程
